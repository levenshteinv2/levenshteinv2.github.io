Typosquatting and Software Supply-Chain Security: Edit Distance, Package Impersonation, Detection, and Defense

Typosquatting and Software Supply-Chain Security: Edit Distance, Package Impersonation, Detection, and Defense

Typosquatting is a name-based attack pattern in which a package, domain, repository, module, library, or other software identifier is made similar enough to a trusted identifier that a user or automated system may select the wrong artifact.

The deceptive name may differ through a missing character, an inserted character, a substitution, a transposition, a separator change, an added prefix or suffix, a Unicode confusable character, or another transformation.

This makes Levenshtein distance useful for detecting nearby identifiers. But string similarity should normally be treated as a candidate-generation signal, not as proof that a package is malicious.

name similarity
↓
candidate generation
↓
context
↓
provenance
↓
package metadata
↓
artifact / behavior analysis
↓
security decision

The central distinction is:

small edit distance
≠
malicious package

Why Package Names Are Security-Sensitive Strings

In ordinary prose, a typo usually changes text. In a software ecosystem, a typo can change which executable artifact is downloaded.

developer intent
↓
package identifier
↓
registry resolution
↓
downloaded artifact
↓
installation or execution

A naming mistake near the beginning of this chain can therefore cross a software trust boundary.

Levenshtein Distance as a First Detection Layer

Let T be the trusted identifier and C a candidate. A simple detector can search for:

dL(T, C) ≤ k

where dL is Levenshtein distance and k is a selected search radius.

Standard Levenshtein distance models:

  • insertion,
  • deletion,
  • substitution.
Transformation Trusted name Variant Unit-cost distance
Deletion package pakage 1
Insertion package packaage 1
Substitution package packege 1

Transpositions Need a Different Operation Model

A common typing mistake swaps adjacent characters:

package
→
pakcage

Classic Levenshtein distance does not include transposition as a primitive operation. An adjacent swap can therefore require two Levenshtein edits even though a user experiences it as one typing error.

For applications where transpositions matter, see Damerau-Levenshtein Distance .

Distance Is Better for Candidate Generation Than Verdicts

A useful security architecture separates two tasks.

CANDIDATE GENERATION

find names that are close
to a protected identifier


SECURITY CLASSIFICATION

decide whether the relationship
is legitimate, accidental,
defensive, or malicious

Levenshtein distance is naturally suited to the first task.

The second requires evidence outside the string itself.

Why a Fixed Distance Threshold Produces False Positives

Software ecosystems contain many legitimate names that differ by only one or two characters.

parser
parsers

color
colors

request
requests

Package names also reuse common vocabulary such as:

  • core,
  • utils,
  • client,
  • server,
  • api,
  • plugin,
  • parser,
  • adapter.

A rule such as:

distance ≤ 1
→
malicious

would therefore create large numbers of false positives.

Name Length Changes the Meaning of an Edit Count

A distance of two can be large for a three-character identifier and small relative to a thirty-character identifier.

A normalized edit distance can be defined as:

d_norm(x,y)
=
dL(x,y)
/
max(|x|, |y|)

and a simple derived similarity as:

sim(x,y)
=
1 - d_norm(x,y)

These values can help compare strings of different lengths, but they still do not encode trust, popularity, visual similarity, ownership, or malicious intent.

Registry Canonicalization Must Be Modeled Explicitly

Package ecosystems can define naming rules involving:

  • case,
  • hyphens,
  • underscores,
  • periods,
  • scopes,
  • namespaces.

A detector should therefore preserve both:

raw identifier
+
registry-canonicalized identifier

Comparing only the raw spelling can miss relationships introduced by registry resolution rules.

Comparing only the canonicalized form can also destroy useful evidence about how the candidate was constructed.

Token Structure Matters

Package identifiers often contain meaningful components:

cloud-storage-client

cloud
storage
client

Character-level edit distance treats the entire identifier as one sequence. A second representation can compare token structure:

d_token(
  tokens(target),
  tokens(candidate)
)

This can reveal relationships that character distance alone handles poorly, such as:

  • added prefixes,
  • added suffixes,
  • token reordering,
  • separator changes,
  • vendor or framework additions.

Combosquatting Is Broader Than Simple Typing Errors

A candidate can preserve the trusted identifier while adding plausible words:

trusted-name
trusted-name-client
trusted-name-security
official-trusted-name

Character edit distance may become relatively large even though the impersonation structure is obvious to a human.

This illustrates a broader principle:

typo similarity
⊂
package-name confusion

Package Confusion Extends Beyond Typosquatting

Research on software package ecosystems shows that developers can be confused through multiple naming mechanisms, not only simple misspellings.

A comprehensive detector therefore should not assume:

package confusion
=
edit distance ≤ small threshold

Lexical similarity is one important signal among several.

Weighted Edit Distance Can Model Typing Behavior

Human substitution errors are not uniformly distributed.

On a particular keyboard layout:

cost(g → h)
<
cost(g → p)

can represent the fact that some keys are physically closer than others.

Similar weighting can model domain-specific error patterns.

See Weighted Levenshtein Distance .

Keyboard weighting should still be treated as an application model rather than universal truth because users may type with different layouts, devices, or input methods.

Unicode Confusables Are a Different Attack Surface

Unicode allows different code points to produce similar visual forms.

A candidate identifier may therefore look close to a trusted identifier even when plain edit distance does not capture the full deception risk.

sequence similarity
≠
visual similarity

Unicode Technical Standard #39 provides dedicated mechanisms for confusable and identifier-security analysis.

See Unicode Homoglyph and Confusable Attacks .

Confusable Processing and Edit Distance Can Be Combined

A defensive system can preserve several representations:

raw identifier
      │
      ├── registry canonical form
      ├── normalized Unicode form
      ├── code-point representation
      ├── grapheme representation
      └── UTS #39 security representation

Edit distance can then be used on the representations appropriate to the task.

This does not turn Levenshtein distance into a visual-similarity metric. Unicode security processing and sequence distance remain separate layers.

Popularity Makes Name Similarity Directional

Standard Levenshtein distance is symmetric:

d(A,B)
=
d(B,A)

Impersonation risk is not.

A newly created, little-used package with a name close to a long-established popular package presents a different hypothesis from two similarly old, independently established projects.

SpellBound demonstrated the practical value of combining lexical similarity with package popularity rather than treating distance alone as the warning criterion.

Package Age and Registration Chronology Add Context

Useful temporal evidence can include:

  • target creation date,
  • candidate creation date,
  • first release date,
  • release frequency,
  • maintainer history.

A candidate that appears long after a well-known target and closely imitates its name may support a stronger impersonation hypothesis.

Conversely, if the candidate predates the supposed target, a simple imitation narrative becomes less plausible.

Ownership and Provenance Are Stronger Than Name Similarity

Similar package names can belong to the same legitimate project family:

framework-core
framework-http
framework-cli
framework-test

Useful evidence includes:

  • maintainer accounts,
  • publisher organization,
  • namespace ownership,
  • repository ownership,
  • verified project domains,
  • release provenance.

Package metadata can help, but metadata supplied by a publisher should not automatically be treated as verified ownership.

Repository and Source Similarity Add Another Layer

A candidate package may copy a legitimate project's source code or documentation.

Useful questions include:

  • Does the candidate reference the same repository?
  • Does repository ownership match the package publisher?
  • Does the repository predate package publication?
  • Does the published artifact correspond to the repository?
  • Was documentation copied from another project?

Source similarity can provide evidence of relationship, but:

similar source
≠
safe source

A nearly identical project can contain a small malicious modification.

See Source Code and AST Similarity .

Typosquatting Is Only One Supply-Chain Attack Strategy

Software supply-chain security includes attack classes where package-name similarity provides little or no signal.

Attack class Name similarity useful? Primary security layer
Classic typosquatting Strongly useful Identifier
Combosquatting Useful with structural features Identifier
Unicode impersonation Partly Identifier + Unicode security
Dependency confusion Often not useful Resolver / namespace
Maintainer compromise No Identity / release
Malicious update No Artifact / behavior
Build compromise No Build provenance

Dependency Confusion Can Have Distance Zero

Dependency confusion can occur when a resolver selects an unintended package from another registry or namespace even though the identifier is exactly the expected name.

intended identifier
=
maliciously resolved identifier

dL = 0

In this case, string similarity contains no discriminating information.

The vulnerability belongs to:

  • registry precedence,
  • namespace configuration,
  • version resolution,
  • private/public dependency policy.

Compromised Legitimate Packages Also Have Distance Zero

If an attacker compromises a maintainer account, repository, build process, or legitimate release channel, the package name can remain completely unchanged.

trusted name
=
compromised name

Detection must then focus on provenance, artifact changes, publisher behavior, signatures, build integrity, and runtime behavior.

This is one of the clearest limits of name-based security detection.

Historical Web Typosquatting Provides the Same Lesson

Typosquatting is not restricted to software package registries. Similar naming attacks have long existed in domain names.

Research examining the early adoption of Let's Encrypt found evidence that some Let's Encrypt certificates were associated with typosquatting and malware-related sites.

This does not imply that Let's Encrypt certificates themselves indicate maliciousness. The important lesson is the opposite:

valid TLS certificate
≠
trusted organizational identity

Transport authentication confirms the domain to which a certificate was issued. It does not establish that a visually or lexically similar domain belongs to the organization a user intended to reach.

See Shedding Light on the Adoption of Let's Encrypt .

Empirical Software Supply-Chain Research

Research on malicious packages has documented real-world supply-chain attacks across ecosystems including npm, PyPI, and RubyGems.

These studies reinforce two points:

  • name impersonation is a genuine software supply-chain technique,
  • software supply-chain compromise includes many techniques beyond name similarity.

See Backstabber's Knife Collection: A Review of Open Source Software Supply Chain Attacks .

Popularity-Aware Detection

A practical warning system can combine:

lexical similarity
+
target popularity
+
candidate popularity
+
package age
+
ownership / provenance

This reduces the mistake of treating every pair of nearby names as equally suspicious.

See SpellBound: Defending Against Package Typosquatting .

Package Confusion Is Broader Than Lexical Distance

A large study of documented package confusion attacks identified multiple mechanisms by which developers can be led to install an unintended package. Many of these mechanisms cannot be reduced to a small character edit.

This is an important boundary for Levenshtein-based detection:

lexically close
→ useful candidate signal

not lexically close
→ does not imply safe

See Beyond Typosquatting: An In-depth Look at Package Confusion .

Pre-Installation Warnings Are Valuable

Package ecosystems can execute code during installation or build stages. A mistaken package selection can therefore become dangerous before an application explicitly imports the package.

Detection close to the package-resolution step has an important advantage:

package requested
↓
candidate appears suspicious
↓
warning / verification
↓
download decision

The earlier the uncertainty is exposed, the less reliance is placed on detecting malicious behavior after installation.

Alert Fatigue Is Part of the Security Model

A detector that warns about every similar package will eventually train users to ignore warnings.

too many alerts
↓
routine warnings
↓
ignored warnings

Because malicious packages are rare compared with legitimate packages, even a small false-positive rate can generate substantial warning volume at registry scale.

Precision therefore matters alongside recall.

Do Not Automatically Correct Security-Sensitive Identifiers

Approximate matching can be useful for:

  • candidate retrieval,
  • warnings,
  • review queues,
  • security investigation.

It should not silently replace a supplied package identifier with the nearest known identifier.

nearest string
≠
intended package

High-consequence systems should preserve uncertainty and require explicit verification rather than silently converting fuzzy similarity into identity.

A Layered Detection Architecture

A practical typosquatting detector can be structured in layers.

protected package set
↓
registry-aware canonicalization
↓
character / token candidate retrieval
↓
Levenshtein / Damerau / weighted features
↓
Unicode confusable analysis
↓
popularity + age + chronology
↓
namespace + maintainer + repository evidence
↓
artifact / dependency / code analysis
↓
behavioral analysis where appropriate
↓
security decision

Each layer answers a different question.

String Similarity Is Evidence, Not Identity

The most important interpretation rule for security applications is:

string similarity
≠
identity

string similarity
≠
ownership

string similarity
≠
trust

string similarity
≠
malicious intent

Levenshtein distance measures sequence difference. Security decisions require evidence about the surrounding system.

This limitation is discussed more broadly in Levenshtein Distance Limitations .

Relationship to Unicode Security

Typosquatting and Unicode confusable attacks meet at the identifier layer, but they require different models.

ordinary typo
→
edit-distance model

adjacent transposition
→
Damerau-style model

keyboard-biased error
→
weighted model

Unicode visual impersonation
→
Unicode security model

package provenance problem
→
ownership / supply-chain model

Combining these representations is more robust than forcing every attack into a single string metric.

Continue with Unicode Homoglyph and Confusable Attacks .

Summary

Typosquatting demonstrates both the usefulness and the limitations of Levenshtein distance.

Edit distance is highly useful for discovering identifiers that differ from a protected name through ordinary insertions, deletions, and substitutions. Damerau-Levenshtein and weighted models can represent additional typo patterns.

But package confusion is broader than typing mistakes. Unicode confusables, prefix and suffix manipulation, semantic naming, dependency confusion, compromised maintainers, malicious updates, and build compromise require additional evidence.

A robust security system therefore uses string distance near the beginning of the investigation rather than as the final verdict.

Use edit distance to find suspicious neighbors. Use provenance, context, Unicode security, artifact analysis, and behavior to decide what they mean.
