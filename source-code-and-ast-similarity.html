Source Code and AST Similarity

Source-code similarity is not one mathematical problem. Two programs can be identical as text, similar after formatting is removed, structurally similar as abstract syntax trees, behaviorally similar under a set of tests, or semantically equivalent despite sharing almost no surface syntax.

These relationships form a hierarchy:

raw characters
      |
      v
tokens
      |
      v
normalized tokens
      |
      v
syntax tree
      |
      v
control/data-flow structure
      |
      v
program behavior
      |
      v
semantic equivalence.

Levenshtein distance is a valuable baseline near the bottom of this hierarchy. It measures the minimum number of insertions, deletions, and substitutions needed to transform one sequence into another. Applied to source code, however, the result depends critically on what the sequence elements are:

characters?

lines?

lexer tokens?

normalized tokens?

AST nodes?

execution events?

Changing the representation changes the meaning of the distance.

This article develops source-code similarity from raw text through tokens and abstract syntax trees, explains tree edit distance and source-code differencing, examines classical clone-detection systems including MOSS, NiCad, Deckard, SourcererCC, and GumTree, and establishes a critical boundary:

source-code similarity
!=
program equivalence.

Two fragments can be nearly identical and behave differently because of one critical operator, constant, API call, or condition. Conversely, two programs can implement the same mathematical function using completely different algorithms and syntax.

1. What does “similar code” mean?

Suppose two source fragments are:

int sum(int a, int b) {
    return a + b;
}

and:

int add(int x, int y) {
    return x + y;
}

They differ textually in:

  • function name;
  • parameter names;
  • formatting choices if present.

Structurally, however, they represent almost the same syntax pattern.

Now compare:

return a + b;

with:

return a - b;

The character and token difference is extremely small, yet program behavior has changed fundamentally.

2. Similarity has multiple representation layers

Representation Typical question
Characters How much literal text changed?
Lines Which source lines were added or removed?
Tokens How similar is the lexical program structure?
Normalized tokens Are fragments similar after renaming or literal normalization?
AST How similar is their syntactic structure?
Control/data-flow Do they organize computation similarly?
Behavior Do they produce similar outputs/effects?
Semantics Do they compute the same function under all relevant inputs?

3. No single representation dominates every task

Raw text is useful for:

  • ordinary diffs;
  • copy detection;
  • format-sensitive review.

ASTs are useful for:

  • structural differencing;
  • refactoring analysis;
  • syntax-aware clone detection.

Behavioral models are needed when the goal approaches:

functional equivalence.

4. Character-level Levenshtein distance

Let source files be character sequences:

A = a1 a2 ... am

B = b1 b2 ... bn.

Character-level edit distance is:

dchar(A,B)
=
minimum number of
character insertions,
deletions,
and substitutions.

5. Character distance is formatting-sensitive

Consider:

if(x){return y;}

and:

if (x) {
    return y;
}

The programs may parse identically while their character sequences differ substantially.

Character edit distance therefore measures:

textual representation difference,

not:

syntactic program difference.

6. Comments distort raw similarity

Compare:

// calculate total
return price * quantity;

with:

return price * quantity;

The executable code is identical, but character distance increases because of a comment.

Whether comments should count depends on the application.

7. String literals create another ambiguity

These fragments differ by only a few characters:

open("production.db");

open("testing.db");

Yet the operational effect can be significant.

A similarity metric cannot infer importance solely from edit count.

8. Identifier length can dominate character distance

int x = lookup(id);

versus:

int customerRecord = lookup(customerIdentifier);

Renaming variables can create many character edits even though the underlying syntax changes little.

9. Character normalization

A preprocessing pipeline may remove:

  • comments;
  • whitespace;
  • formatting;
  • some literal differences.

Then distance is computed on the transformed text.

But preprocessing changes the question.

10. Normalization creates invariance

If whitespace is removed, the similarity measure becomes invariant to whitespace changes.

If comments are removed, it becomes invariant to comments.

If identifiers are renamed to placeholders, it becomes invariant to many identifier changes.

This general principle is:

normalization
=
deliberately declaring
some differences irrelevant.

11. Over-normalization can hide important differences

If every literal becomes:

LITERAL

then:

timeout = 5;

and:

timeout = 500000;

can become structurally identical.

For some clone-detection tasks that is desirable.

For security review it may be disastrous.

12. Line-level comparison

Traditional source-control diffs usually compare sequences of lines.

This representation is convenient because developers edit files visually as lines.

But source-language syntax does not necessarily follow line boundaries.

13. One formatting operation can create many line changes

Reformatting:

call(a, b, c);

into:

call(
    a,
    b,
    c
);

produces substantial line-level difference without meaningful syntax change.

14. Line diff is optimized for review, not semantic modeling

This distinction should remain explicit:

human-readable diff
!=
program-structure distance.

15. Lexical tokenization

A lexer converts source text into tokens such as:

KEYWORD
IDENTIFIER
OPERATOR
LITERAL
PUNCTUATION.

For:

return total + tax;

a simplified token sequence might be:

RETURN
IDENT(total)
PLUS
IDENT(tax)
SEMICOLON.

16. Token edit distance

After tokenization, compute:

dtoken(
  tokens(A),
  tokens(B)
).

Whitespace and comment changes can disappear automatically when the lexer ignores them.

17. Token distance better respects language syntax

Changing:

customerIdentifier

to:

id

changes one identifier token instead of many characters.

This often makes token distance more appropriate for code similarity.

18. Identifier normalization

A detector can transform:

IDENT(x)
IDENT(total)
IDENT(customer)

into:

IDENT
IDENT
IDENT.

This allows renamed copies to remain highly similar.

19. Consistent renaming versus blind renaming

There are two very different normalization strategies.

Blind normalization:

all identifiers
->
IDENT.

Consistent normalization:

first unique identifier -> VAR_1
second unique identifier -> VAR_2
...

Consistent renaming preserves alias relationships.

20. Why alias relationships matter

Compare:

return x + x;

with:

return x + y;

Blind identifier normalization produces:

RETURN IDENT + IDENT

for both.

Consistent renaming can preserve:

VAR_1 + VAR_1

versus:

VAR_1 + VAR_2.

21. Literal normalization

Literal values may be transformed by type:

123
->
INT_LITERAL

"hello"
->
STRING_LITERAL.

This increases tolerance to copied code with changed constants.

22. Literal identity may still matter

In security and correctness analysis:

permissions = 0644

versus:

permissions = 0777

is not a negligible difference.

Thus detector configuration must match its task.

23. Token multiset similarity

Some systems do not preserve complete token ordering.

A fragment can be represented by token frequencies:

f(token).

Similarity may then use:

  • Jaccard similarity;
  • cosine similarity;
  • overlap coefficients.

24. Multisets trade order for scalability

Token frequency representations tolerate certain reorderings but discard sequence information.

Therefore:

same tokens
!=
same program.

25. Example of order destroying semantics

authenticate();
deleteAccount();

versus:

deleteAccount();
authenticate();

The token multiset can be almost identical.

Behavior is not.

26. Token n-grams

Another representation uses windows:

(t1,t2,...,tq).

These preserve local ordering while remaining indexable.

27. Fingerprinting

Token or character n-grams can be hashed:

gram
->
hash.

A program fragment is then represented by selected fingerprints.

This allows large-scale retrieval without comparing every pair directly.

28. Winnowing

Schleimer, Wilkerson, and Aiken introduced the winnowing local fingerprint-selection algorithm in 2003.

The method selects hashes from overlapping windows while providing guarantees about sufficiently long exact matching substrings under its parameterization.

See Winnowing: Local Algorithms for Document Fingerprinting.

29. MOSS

MOSS—Measure of Software Similarity—is a long-running Stanford service used especially for detecting unusually similar programming assignments.

The official MOSS documentation emphasizes an important distinction:

MOSS detects program similarity.

MOSS does not automatically
prove plagiarism.

See A System for Detecting Software Similarity.

30. Similarity is evidence, not intent

Code can be similar because of:

  • copying;
  • shared assignment requirements;
  • common libraries;
  • standard algorithms;
  • generated templates;
  • independent convergence.

Therefore:

high code similarity
!=
proof of plagiarism.

31. The same principle applies to software provenance

A cloned code fragment does not automatically establish:

  • which project copied which;
  • whether copying was licensed;
  • whether both derived from a third source;
  • whether resemblance was independently produced.

32. Code clones

A code clone is a code fragment similar to another fragment according to a specified syntactic or semantic relationship.

There is no single universally sufficient similarity criterion.

33. Common four-type clone taxonomy

A widely used taxonomy distinguishes:

Type 1
Type 2
Type 3
Type 4.

Roy, Cordy, and Koschke organize clone-detection techniques around these increasingly difficult scenarios in their 2009 survey. See Comparison and evaluation of code clone detection techniques and tools.

34. Type-1 clones

Type-1 clones are effectively identical except for differences such as:

  • whitespace;
  • layout;
  • comments.

These are close to textual copies.

35. Type-2 clones

Type-2 clones additionally allow systematic differences such as:

  • identifier names;
  • literal values;
  • types.

Normalization is especially useful here.

36. Type-3 clones

Type-3 clones contain further statement-level changes such as:

  • inserted statements;
  • deleted statements;
  • modified statements.

They are often called near-miss clones.

37. Type-4 clones

Type-4 generally refers to fragments that implement equivalent or strongly similar functionality despite substantial syntactic difference.

This category is much harder because the detector must move beyond surface resemblance.

38. Clone types are not mathematical natural constants

The boundaries between Type-2, Type-3, and Type-4 depend on definitions, normalization, granularity, and benchmark methodology.

Therefore:

clone type
should always be interpreted
under the taxonomy used
by the study.

39. Clone granularity

Clones can occur at different levels:

  • expression;
  • statement sequence;
  • block;
  • function;
  • method;
  • class;
  • file;
  • subsystem.

A detector optimized for function clones may miss short copied expressions.

40. Minimum clone size

Almost every practical detector sets some minimum size:

minimum tokens

minimum lines

minimum AST nodes.

Otherwise trivial syntax patterns create enormous numbers of meaningless matches.

41. Small fragments are naturally non-unique

For example:

return null;

may occur independently in thousands of projects.

Literal similarity alone provides little evidence of copying.

42. Clone detection has a base-rate problem

Large software corpora contain enormous numbers of syntactically routine fragments.

Even a highly precise detector can generate many matches unless candidate granularity and minimum size are carefully chosen.

43. Parsing source code

An abstract syntax tree is constructed by parsing source according to a language grammar.

For:

x = a + b * c;

a simplified AST might be:

Assignment
├── Identifier(x)
└── Add
    ├── Identifier(a)
    └── Multiply
        ├── Identifier(b)
        └── Identifier(c)

44. AST preserves syntax hierarchy

The AST records that:

b * c

is grouped beneath the addition.

A flat token sequence preserves order but does not explicitly expose this hierarchy.

45. AST is abstract

Depending on the parser, ASTs may omit:

  • whitespace;
  • comments;
  • parentheses that do not change structure;
  • certain punctuation;
  • syntactic sugar.

This makes AST comparison naturally insensitive to many textual changes.

46. There is no universal AST

The same language can have different AST representations depending on:

  • compiler;
  • parser framework;
  • language version;
  • desugaring stage;
  • node granularity.

Therefore:

AST similarity score
is representation-dependent.

47. Concrete syntax tree versus AST

A concrete syntax tree preserves more grammar-level details.

An AST typically removes syntactic structure considered unnecessary for semantic processing.

Comparisons at these two levels produce different edit scripts.

48. AST normalization

An AST can itself be normalized.

For example:

Identifier("customer")
->
Identifier

or:

IntegerLiteral(123)
->
IntegerLiteral.

This increases clone tolerance but discards information.

49. AST fingerprints

Instead of computing exact tree distance, a subtree can be mapped to a feature vector:

v(T)
=
[
count(NodeType_1),
count(NodeType_2),
...
].

Vector similarity then approximates structural similarity.

50. Deckard

Deckard is a prominent tree-based clone detector introduced by Jiang, Misherghi, Su, and Glondu.

It characterizes AST subtrees using numerical vectors and clusters nearby vectors to find clone candidates.

See DECKARD: Scalable and Accurate Tree-Based Detection of Code Clones.

51. Deckard is not exact tree edit distance

This distinction is important.

Deckard maps syntax-tree structure into vectors and performs similarity search in vector space.

It does not simply compute exact Zhang-Shasha tree edit distance between every pair of ASTs.

52. Why vectorization helps scale

Computing exact structural distance for every pair of fragments would require an enormous number of pairwise comparisons.

Vector representations allow:

feature extraction
+
clustering/indexing
+
candidate comparison.

53. Vectorization loses structure

Two trees can have similar node-count vectors but very different arrangements.

Therefore:

vector similarity
!=
tree isomorphism
!=
tree edit distance.

54. Tree edit distance

The general mathematical extension of string edit distance to trees is tree edit distance.

For ordered labeled trees, standard primitive operations typically include:

insert node

delete node

relabel node.

55. Ordered labeled trees

An ordered tree distinguishes sibling order.

Thus:

Add(a,b)

and:

Add(b,a)

have different ordered representations even if the operator happens to be mathematically commutative.

56. Tree edit distance is syntax-sensitive, not algebra-aware

For integer addition without overflow concerns in a simplified mathematical model:

a + b

and:

b + a

may be semantically equivalent.

The ASTs still differ by child ordering.

57. Zhang-Shasha tree edit distance

Zhang and Shasha's 1989 algorithm is a foundational dynamic-programming method for ordered labeled tree edit distance.

See Simple Fast Algorithms for the Editing Distance between Trees and Related Problems.

58. Zhang-Shasha complexity

For trees T1 and T2, the published sequential complexity is:

O(
 |T1| |T2|
 min(depth(T1), leaves(T1))
 min(depth(T2), leaves(T2))
)

with:

O(|T1||T2|)

space.

The runtime therefore depends not only on tree sizes but also on tree shape.

59. Why tree distance is harder than string distance

A string has one linear order.

A tree contains:

  • hierarchy;
  • parent-child constraints;
  • sibling order;
  • subtree structure.

An edit must preserve a valid tree mapping.

60. Node relabeling costs

A tree-distance implementation must decide whether:

Identifier(x)
->
Identifier(y)

costs:

1

or perhaps:

0

after identifier normalization.

Thus AST distance depends strongly on node labels and cost functions.

61. Typed edit costs

A syntax-aware cost model might distinguish:

Identifier rename      low cost

Literal change         medium cost

operator change        higher cost

control node change    higher cost.

This is analogous to weighted edit distance.

62. Arbitrary weights need not produce a metric

If edit costs violate symmetry or triangle inequality, the resulting score should not automatically be called a metric.

This matters because metric indexes rely on metric properties.

63. AST edit distance versus source-code differencing

These problems overlap but are not identical.

Tree edit distance asks:

What minimum-cost tree operations
transform T1 into T2?

Source differencing often asks:

What change sequence best explains
what a developer actually did?

64. Move operations

Traditional tree edit distance with only:

insert
delete
relabel

may represent a moved subtree as:

delete old subtree
+
insert new subtree.

Human developers would often describe it simply as:

move.

65. GumTree

Falleri, Morandat, Blanc, Martinez, and Monperrus introduced GumTree for fine-grained source-code differencing at AST granularity.

The method explicitly supports move actions and seeks edit scripts that are short and close to developer intent.

See Fine-grained and accurate source code differencing.

66. GumTree is not simply “Levenshtein on AST nodes”

GumTree performs tree mapping and differencing with heuristics designed for source evolution.

Its goal differs from computing an exact classical tree-edit-distance value.

Therefore:

GumTree edit script
!=
necessarily minimum Zhang-Shasha script.

67. Shortest edit script and most intuitive edit script can differ

Suppose a developer moves a method from one class to another.

One cost model may find:

delete subtree
+
insert subtree

cheap enough.

A source-differencing tool may instead prefer:

move method.

The second representation better matches developer intent.

68. AST mapping is fundamental

Before describing edits, a differencer needs to determine which node in the old tree corresponds to which node in the new tree.

This is the tree-matching problem.

69. Mapping ambiguity

Repeated structures create multiple plausible mappings.

For example:

if (x) log();
if (y) log();

contains repeated call nodes.

After one block is moved, determining node identity is not always trivial.

70. Mapping quality changes the edit script

A poor mapping can turn:

one move

into:

many deletes
+
many inserts.

Thus edit-script quality is not determined by operation costs alone.

71. APTED and robust tree edit distance

Pawlik and Augsten developed improved algorithms for tree edit distance that choose robust decomposition strategies and control memory usage.

See Tree edit distance: Robust and memory-efficient.

These algorithms address exact tree edit distance rather than source-specific developer-intent differencing.

72. AST size matters

A source file of:

1,000 lines

may contain thousands of AST nodes.

Pairwise tree distance over a repository can therefore become expensive rapidly.

73. Candidate generation before exact tree comparison

A scalable system should normally use:

cheap fingerprints / filters
        |
        v
candidate pairs
        |
        v
expensive structural comparison.

This is the same filter-and-verify architecture used in edit-distance indexing and filtering.

74. NiCad

NiCad takes a parser-based but deliberately lightweight approach.

It uses flexible pretty-printing and normalization so near-miss differences can be compared effectively at the text-line level after syntax-aware transformation.

See Roy and Cordy, NICAD: Accurate Detection of Near-Miss Intentional Clones Using Flexible Pretty-Printing and Code Normalization.

75. NiCad illustrates a powerful principle

A detector does not always need the most sophisticated distance measure.

Sometimes the better strategy is:

transform code
into a representation
where a simpler comparison
becomes informative.

76. Representation engineering can outperform metric complexity

Compare two strategies:

A:
raw text
+
complex similarity

B:
careful normalization
+
simple similarity.

Depending on the clone type, strategy B can be more robust and easier to scale.

77. SourcererCC

SourcererCC is a token-based clone detector designed for very large source repositories.

It uses an optimized inverted index and filtering heuristics to reduce candidate comparisons.

See SourcererCC: Scaling Code Clone Detection to Big Code.

78. SourcererCC demonstrates retrieval architecture

source blocks
    |
    v
token representation
    |
    v
inverted index
    |
    v
filtering
    |
    v
candidate blocks
    |
    v
token-overlap verification.

79. Why all-pairs comparison is impossible at Big Code scale

For:

N

fragments, naïve pairwise comparison requires:

N(N-1)/2

comparisons.

At millions of fragments this is prohibitive.

80. Filtering is not merely an optimization

At repository scale, candidate retrieval is part of the algorithmic definition of a practical detector.

The challenge becomes:

eliminate most impossible pairs

without eliminating true clones.

81. Recall-preserving filters

A good filter uses necessary conditions for similarity.

For example, if a token-overlap threshold is required, fragments with insufficient maximum possible overlap can be rejected without full comparison.

82. Heuristic filters

Other filters trade some recall for speed.

The benchmark must make this trade-off visible.

83. Candidate generation and classification should be separated

Like fuzzy search:

retrieval
!=
final similarity judgment.

A broad candidate generator can prioritize recall while a stronger verifier prioritizes precision.

84. Code similarity as information retrieval

A repository can be treated as a collection of code documents.

A query fragment retrieves:

nearest code fragments.

This enables:

  • clone search;
  • example search;
  • license analysis;
  • bug-pattern search;
  • reuse recommendation.

85. Search similarity and clone definition are different

A code-search system can return loosely related results.

A clone detector usually needs a more explicit relationship.

Therefore a ranking model cannot automatically be interpreted as a clone classifier.

86. BigCloneBench

Large-scale clone detection needs curated benchmarks containing realistic clone relationships.

BigCloneBench was introduced as a benchmark of inter-project Java clones derived from the IJaDataset.

See Towards a Big Data Curated Benchmark of Inter-Project Code Clones.

87. BigCloneBench evaluation

Svajlenko and Roy later described systematic evaluation of clone detectors using BigCloneBench.

See Evaluating Clone Detection Tools with BigCloneBench.

88. Precision and recall

precision
=
true clone reports
/
all clone reports

recall
=
detected true clones
/
all true clones.

Both matter.

89. High recall with unusable precision

A detector that reports almost every pair as similar can achieve high recall.

It is operationally useless.

90. High precision with tiny recall

A detector that reports only byte-identical fragments may have excellent precision while missing most near-miss clones.

91. Clone benchmarks are difficult to construct

For a large code corpus, the number of possible fragment pairs is enormous.

No human team can manually classify every pair.

Benchmark construction therefore relies on sampling, search, heuristics, and manual validation.

92. Ground truth is representation-dependent

Humans may disagree about whether two weakly similar fragments should be considered clones.

This becomes especially difficult near the Type-3/Type-4 boundary.

93. Bellon benchmark

Bellon, Koschke, Antoniol, Krinke, and Merlo conducted an influential comparative evaluation of clone-detection tools and built a manually validated corpus of candidate clones.

See Comparison and Evaluation of Clone Detection Tools.

94. Benchmark bias

If benchmark candidates were originally generated by particular detector families, the benchmark may overrepresent clone forms those detectors can discover.

This general problem is:

detector-generated ground truth
can inherit detector bias.

95. Mutation-based benchmarks

Another strategy creates artificial clones through controlled transformations:

rename identifier

change literal

insert statement

delete statement

reorder code.

This gives exact knowledge of how the clone was generated.

96. Synthetic clones are not fully realistic

Artificial mutation distributions may not reflect real developer edits.

A good evaluation should therefore combine:

real clones
+
synthetic controlled cases.

97. AST similarity can detect refactorings

Examples include:

  • method extraction;
  • method movement;
  • identifier renaming;
  • statement insertion;
  • statement deletion.

But each refactoring may require a different structural model.

98. Move detection

Suppose:

statement block B

moves from one location to another.

A line diff may show:

many deletions
+
many additions.

An AST differencer can identify:

MOVE(B).

99. Move similarity is not universal tree edit distance

Adding move as a primitive changes the edit model.

If:

move cost = 1,

large structural relocation can become extremely cheap.

Whether that is desirable depends on the task.

100. Function extraction

Consider:

void process() {
    validate();
    normalize();
    save();
}

becoming:

void process() {
    prepare();
    save();
}

void prepare() {
    validate();
    normalize();
}

Textual distance is substantial.

The logic represented by:

validate();
normalize();

has mostly moved into another method.

101. AST-only local comparison can still miss extraction relationships

If methods are compared independently, one original method may map to two new methods.

This is no longer a simple one-tree-to-one-tree problem.

102. Program differencing may require graph relationships

Refactoring analysis can require:

  • call graphs;
  • symbol resolution;
  • type information;
  • data flow.

An AST is only one layer.

103. Control-flow graph

A control-flow graph represents possible execution transitions between program locations.

statement
   |
   v
branch
 /    \
v      v
...

Two fragments with different syntax can have similar control flow.

104. AST and CFG answer different questions

AST:
How is the program syntactically constructed?

CFG:
How can control move during execution?

105. Data-flow graph

Data-flow relationships model how values are defined, transformed, and used.

For example:

input
  |
  v
sanitize
  |
  v
query.

Renaming variables does not alter the basic dependency structure.

106. Data flow can expose semantic similarity

Two code fragments may use different variable names and syntax while performing similar sequences of data transformations.

This is why structural code models increasingly incorporate data flow.

107. Program dependence graph

A program dependence graph combines relationships such as:

  • control dependence;
  • data dependence.

Graph-based matching can detect similarities invisible to text or AST-only methods.

108. Graph comparison is more expensive

Moving from strings to trees to general graphs usually increases algorithmic difficulty.

This is discussed more generally in tree and graph edit distance.

109. Type-4 clones challenge syntax-based methods

Consider two implementations of factorial:

int factorial(int n) {
    int r = 1;

    for (int i = 2; i <= n; i++)
        r *= i;

    return r;
}

and:

int factorial(int n) {
    if (n <= 1)
        return 1;

    return n * factorial(n - 1);
}

Both compute factorial in the intended domain.

The syntax trees are radically different.

110. AST distance can be large while behavior is similar

This illustrates:

structural similarity
is neither necessary
nor sufficient
for semantic equivalence.

111. Near-identical ASTs can behave differently

if (isAuthorized(user))
    allow();

versus:

if (!isAuthorized(user))
    allow();

One inserted negation node creates a tiny structural edit.

The security semantics are reversed.

112. Semantic importance is nonuniform

Uniform edit cost assumes:

one changed AST node
≈
one unit of difference.

Program meaning does not behave that way.

Changing one node from:

<

to:

<=

can introduce an important boundary bug.

113. One literal can dominate semantics

MAX_RETRIES = 3

versus:

MAX_RETRIES = 3000000.

The AST difference may be one literal node.

Operational behavior is very different.

114. One API call can dominate semantics

hashPassword(password)

versus:

storePlaintext(password).

Syntactic structure can remain highly similar.

Security meaning does not.

115. AST similarity should not be used as proof of software safety

A malicious package can copy nearly all legitimate source code and add one harmful statement.

This issue is particularly relevant to software supply-chain security.

116. Delta analysis is often more useful than aggregate similarity

If two packages are:

99.9% similar,

the security question is not:

Are they mostly alike?

It is:

What is inside the 0.1% difference?

117. Similarity score hides localization

A scalar such as:

0.98 similarity

does not identify:

  • which code differs;
  • how it differs;
  • whether the difference is security-critical.

118. Always preserve the edit script

For review applications, return:

similarity score
+
matching regions
+
edit script
+
changed symbols.

The explanation is often more useful than the scalar.

119. Semantic clones

Semantic clone detection attempts to identify programs with similar functionality even when syntactic resemblance becomes weak.

This can involve:

  • program metrics;
  • execution traces;
  • graphs;
  • symbolic representations;
  • machine-learned embeddings.

120. The “twilight zone”

Saini and colleagues described a difficult region between strongly syntactic Type-3 clones and purely semantic Type-4 clones.

Their Oreo system combines software metrics, information retrieval, and machine learning to target this weakly syntactic region.

See Oreo: Detection of Clones in the Twilight Zone.

121. Semantic similarity is itself underspecified

“Same functionality” can mean:

same outputs for tested inputs

same mathematical function

same observable side effects

same business purpose

same algorithmic intent.

These are not equivalent definitions.

122. Behavioral equivalence

A strong functional relationship might require:

for every valid input x:

A(x) = B(x).

For stateful programs it may additionally require equivalent:

  • state transitions;
  • exceptions;
  • I/O;
  • timing-sensitive effects;
  • external calls.

123. Tests provide evidence, not universal equivalence

If two functions pass the same 1,000 test cases:

behavior agreed
on those 1,000 cases.

It does not logically establish:

behavior agrees
for every possible input.

124. Dynamic behavioral fingerprints

Execute both functions on a controlled input set:

X =
{x1,x2,...,xk}.

Construct:

F(P)
=
[
P(x1),
P(x2),
...
P(xk)
].

Then compare behavioral fingerprints.

125. Behavioral fingerprints depend on the test distribution

Two incorrect implementations can agree on easy inputs while diverging on:

  • boundary cases;
  • overflow;
  • null input;
  • malformed input;
  • concurrency;
  • large values.

126. Side effects complicate behavioral similarity

A function can return the same value while additionally:

  • writing a file;
  • sending network traffic;
  • logging credentials;
  • modifying global state.

Output equality alone is not semantic equivalence.

127. Symbolic execution

Symbolic execution can reason about program paths using symbolic inputs instead of enumerating only concrete examples.

It can help establish equivalence for bounded or tractable fragments.

But path explosion limits general scalability.

128. Program equivalence is much harder than edit distance

For unrestricted general programs, semantic equivalence is not a problem reducible to one simple string metric.

This is an essential boundary for any similarity system.

129. Neural code representations

Modern models can map code into learned vectors:

code
->
embedding z ∈ R^d.

Similarity is then often measured with cosine similarity or another vector-space measure.

130. CodeBERT

CodeBERT is a pretrained model designed to learn general-purpose representations for programming language and natural language.

See CodeBERT: A Pre-Trained Model for Programming and Natural Languages.

131. Learned embeddings are not edit distances

A model embedding can assign high similarity to syntactically distant code.

This is useful for semantic retrieval.

But:

embedding similarity
!=
minimum edit count.

The distinction is developed more generally in learned edit distance and embeddings.

132. Learned similarity depends on training data

A model learns relationships present in:

  • training repositories;
  • pretraining objectives;
  • tokenization;
  • language distribution;
  • fine-tuning labels.

It is therefore not a universal semantic oracle.

133. Embedding similarity can reflect superficial correlations

A model may rely partly on:

  • identifier names;
  • API names;
  • comments;
  • common coding templates.

High embedding similarity should be validated against the actual task.

134. Data-flow-aware learned models

GraphCodeBERT extends sequence-oriented code representation by incorporating code data-flow structure during pretraining.

This reflects a broader trend:

tokens
+
program structure
+
learned representations.

But structural attention still does not constitute formal semantic equivalence.

135. Cross-language similarity

The same algorithm can be implemented in:

Python
Java
C++
Rust.

Raw text and language-specific ASTs may differ completely.

136. Language-independent intermediate representations

Cross-language analysis can map programs toward:

  • normalized tokens;
  • generic AST schemas;
  • control-flow representations;
  • intermediate representations;
  • learned embeddings.

137. Generic AST schemas lose language-specific information

Collapsing several languages into common node categories improves cross-language comparison but can hide important language semantics.

138. Compiler IR

Compiled languages can sometimes be compared using compiler intermediate representations.

Different source syntax may lower into similar IR patterns.

However optimization levels can transform the representation heavily.

139. Compiler optimization can increase or reduce similarity

Inlining, constant folding, loop unrolling, and dead-code elimination can alter structural relationships.

Therefore:

IR similarity
depends on
compiler + version + optimization flags.

140. Binary similarity is another distinct problem

Comparing compiled binaries introduces:

  • instruction selection;
  • register allocation;
  • addresses;
  • compiler transformations.

Source-code similarity results should not automatically be generalized to binary similarity.

141. Generated code

Generated source can contain enormous repeated structures.

A clone detector may report thousands of technically correct but operationally useless matches.

Generated code should often be tagged or filtered separately.

142. Framework boilerplate

Framework-generated patterns produce similar code independently across projects.

Similarity does not imply shared authorship.

143. Standard algorithms

Implementations of:

  • binary search;
  • quicksort;
  • CRC;
  • well-known parsing patterns;

can converge naturally.

Common algorithm structure weakens provenance inference.

144. API constraints create convergent code

If a library requires:

create()
configure()
execute()
close()

many independent programs will contain the same call sequence.

145. License analysis needs more than clone detection

A similarity detector can identify candidate reused code.

Determining licensing implications requires:

  • source provenance;
  • license text;
  • copyright history;
  • jurisdiction;
  • actual derivation evidence.

146. Similarity is not legal conclusion

similar code
!=
copyright infringement.

The detector can support investigation but should not make legal conclusions automatically.

147. Vulnerability clone detection

Once a vulnerable code fragment is known, clone search can locate structurally similar instances elsewhere.

This can help identify copied bugs.

148. Vulnerability patch search

AST differencing can derive a patch pattern:

before AST
->
after AST.

Repositories can then be searched for related unpatched structures.

149. Structural similarity does not guarantee same vulnerability

Context matters:

  • input validation;
  • callers;
  • types;
  • environment;
  • data-flow constraints.

150. One clone can be safe and another unsafe

Identical helper code may be reachable with attacker-controlled input in one application and only trusted input in another.

Security is contextual.

151. Patch similarity and behavior similarity differ

Two developers may fix the same vulnerability using completely different syntax.

A patch-clone detector based only on AST distance may miss this relationship.

152. Refactoring versus semantic change

Source-history analysis often tries to distinguish:

refactoring

from:

behavioral modification.

AST differencing can provide strong evidence but cannot universally establish behavioral preservation.

153. Rename refactoring

A symbol rename can produce many textual differences:

oldName
->
newName.

Symbol-aware analysis can represent the entire operation as one logical refactoring.

154. Textual distance overcounts correlated edits

If one identifier occurs 200 times, renaming it can produce:

200 substitutions

at token level.

A refactoring model sees:

one rename operation.

155. Edit granularity controls distance meaning

This is a general principle:

fine-grained operations
->
large edit counts

high-level operations
->
smaller conceptual edit counts.

156. There is no universally correct operation vocabulary

Possible operations include:

insert character

replace token

rename identifier

move subtree

extract method

inline method

change API.

Each defines a different distance space.

157. Fine-grained distance is objective only relative to its model

A minimum edit path is mathematically exact once:

  • representation;
  • operations;
  • costs

are fixed.

It is not automatically the uniquely correct interpretation of the developer's change.

158. Multiple optimal edit scripts

Just as string edit distance can have multiple minimum edit scripts, tree differencing can have multiple equally cheap mappings.

Repeated code increases ambiguity.

159. Tie-breaking matters

A differencer should specify how it chooses among equally plausible mappings.

Otherwise output may vary across implementations despite identical distance.

160. Stable diffs matter operationally

Developers expect small unrelated edits not to completely reorder a diff's interpretation.

Stability can therefore be more important than mathematically minimal operation count.

161. Normalized similarity score

A distance can be converted into a score such as:

sim(A,B)
=
1
-
d(A,B)
/
max(size(A),size(B)).

But this formula is only one convention.

162. Normalization denominator matters

Alternatives include:

max size

mean size

sum size

smaller size.

Different choices produce different numerical interpretations.

163. Thresholds are domain-dependent

A rule such as:

similarity >= 0.8

has no universal meaning.

The appropriate threshold depends on:

  • representation;
  • fragment size;
  • clone type;
  • language;
  • normalization;
  • application.

164. Small fragments require stricter thresholds

A 90% similarity between ten tokens can arise by chance much more easily than between ten thousand tokens.

Similarity should therefore be interpreted with fragment length.

165. Statistical significance of similarity

For provenance analysis, one can ask:

How likely is this amount
of similarity
under independent code generation?

This requires a background model of the software domain, not edit distance alone.

166. Common language syntax creates a nonuniform background

Tokens such as:

if
return
for
{
}
=

are extremely common.

Rare identifier or structural sequences can provide stronger evidence than common syntax.

167. Weighted information retrieval

Instead of counting all tokens equally, one can assign inverse-document-frequency-style weights:

idf(t)
=
log(
 N / df(t)
).

Rare tokens receive greater influence.

168. Rare does not mean semantically important

A generated UUID in a comment may be rare but irrelevant.

Weighting should remain representation-aware.

169. Clone genealogies

Once clones are discovered across version history, one can track:

origin

copy

modification

divergence

deletion.

This creates clone genealogies.

170. Temporal evidence helps provenance inference

If fragment A appears years before fragment B, A is a more plausible source than B.

But chronology alone does not prove direct copying because both may derive from another source.

171. Version history changes clone analysis

A detector operating only on current snapshots cannot see:

  • when code appeared;
  • when it diverged;
  • which repository first contained it.

172. Repository forks

Forks naturally contain massive clone relationships.

A clone detector without repository genealogy can treat ordinary fork inheritance as suspicious duplication.

173. Deduplicate known forks before cross-project analysis

For large-scale provenance studies, identify:

  • fork relationships;
  • mirrors;
  • vendor copies;
  • generated bundles.

before interpreting clone counts.

174. Third-party vendoring

Repositories often copy dependencies directly into:

vendor/
third_party/
external/.

These similarities may be intentional and licensed.

175. Path information can be useful metadata

A clone inside:

third_party/

has different provenance implications from a clone inside an independently named application module.

176. Comments can be weak or strong evidence

Comments are usually discarded for structural clone detection.

For provenance investigation, an unusual identical comment or typo can be valuable evidence.

Thus a system may maintain both:

semantic-normalized representation

and

forensic raw representation.

177. Security-sensitive Unicode

Identifiers can contain visually confusable Unicode characters.

Two source fragments can look nearly identical while token identities differ.

This is covered in Unicode homoglyph and confusable attacks.

178. Normalize Unicode carefully

Unicode canonical normalization can eliminate representation-only differences.

But:

normalization
!=
confusable detection.

Source-code security needs both where Unicode identifiers are allowed.

179. AST parser must see the actual compiler semantics

If a comparison parser interprets source differently from the production compiler, AST-based analysis may become misleading.

Language-version compatibility matters.

180. Preprocessor languages complicate parsing

C and C++ source can depend heavily on:

  • macros;
  • conditional compilation;
  • include files.

The raw source AST and post-preprocessing AST can be very different.

181. Compare preprocessor configuration explicitly

The same file can compile into different programs under:

-DDEBUG

-DPLATFORM_X

-DFEATURE_Y.

A syntax comparison without configuration may not represent deployed behavior.

182. Generated macro code

One macro definition can expand into many repeated structures.

Clone detection after expansion can therefore greatly inflate duplicate counts.

183. Template and generic instantiation

Compilers may instantiate many specialized versions of one generic definition.

Similarity at generated IR level can therefore reflect compiler expansion rather than developer duplication.

184. Code formatting tools can collapse Type-1 differences

If every fragment is passed through a deterministic formatter:

formatting variability
->
canonical layout.

Then simple line comparisons become much more informative.

185. Formatter version must be recorded

Formatting output can change across versions.

Reproducible analysis should record:

  • formatter;
  • version;
  • configuration.

186. Parser configuration must also be recorded

Report:

language version

parser

parser version

preprocessor flags

normalization rules.

Otherwise AST similarity results may not be reproducible.

187. Benchmark multiple representations

A rigorous similarity study can compare:

raw text

normalized text

tokens

normalized tokens

AST

learned embedding.

This reveals which representation provides the useful invariances.

188. Ablation testing

Remove individual preprocessing steps:

without comment removal

without identifier normalization

without literal normalization

without AST abstraction.

Measure the effect on precision and recall.

189. Do not hide preprocessing inside the detector

A reported “similarity algorithm” can owe much of its performance to normalization rather than the final comparison function.

Document both.

190. Runtime benchmark

Report:

  • parsing time;
  • index construction time;
  • query time;
  • verification time;
  • peak memory;
  • index size.

191. Throughput benchmark

For large repositories, useful measures include:

files / second

functions / second

million lines / hour

candidate pairs / query.

192. Scaling curve

Do not report only one corpus size.

Measure:

10^3 fragments

10^4

10^5

10^6

...

to reveal algorithmic scaling.

193. Candidate explosion

Highly repetitive corpora can produce many near matches.

Even efficient indexes can degrade when:

almost everything
resembles everything else.

194. Boilerplate-aware filters

One mitigation is to downweight or remove highly frequent fragments.

But this risks hiding real vulnerabilities copied inside boilerplate.

195. Precision should be stratified by clone type

A single aggregate score can hide behavior such as:

excellent Type-1 recall

good Type-2 recall

poor Type-3 recall

almost no Type-4 recall.

196. Recall should also be stratified by similarity strength

BigCloneBench-based studies often distinguish strong and weak syntactic clone relationships because difficulty changes across the spectrum.

197. Inter-project versus intra-project clones

Intra-project clone search asks:

Where is code duplicated
inside one software system?

Inter-project clone search asks:

Where does similar code occur
across projects?

The latter requires much greater scaling and provenance context.

198. Clone management

Detection is only the first stage.

Teams may need to:

  • track clones;
  • synchronize fixes;
  • refactor duplicate code;
  • document intentional duplication.

199. Duplicate code is not always bad

Cloning can sometimes be intentional because of:

  • performance;
  • platform isolation;
  • dependency avoidance;
  • generated code;
  • temporary development strategy.

Clone detection should not automatically trigger refactoring.

200. Refactoring clones can increase coupling

Combining two superficially similar fragments into one abstraction can create a bad abstraction if their future evolution differs.

Similarity is not proof that deduplication is architecturally correct.

201. Clone divergence

Duplicated fragments can gradually evolve independently.

This produces:

original clone
      |
      +---- branch A changes
      |
      +---- branch B changes.

Type-3 clones often arise through this process.

202. Inconsistent clone updates

A bug fix may be applied to one copy but not another.

Clone detection can locate sibling fragments requiring review.

203. AST differencing helps compare clone evolution

Given clone versions:

A_old -> A_new

B_old -> B_new,

compare their structural edit scripts.

If one branch receives a security fix and the other does not, the difference becomes visible.

204. Patch-equivalence detection

Two patches may be structurally equivalent despite applying to renamed code.

Normalize identifiers and compare AST edit patterns rather than raw textual patches.

205. But equivalent edit scripts do not guarantee equivalent effects

The surrounding types, APIs, and control flow may differ.

Patch interpretation remains contextual.

206. Code review application

A syntax-aware diff can answer:

Which expression changed?

Which method moved?

Which identifier was renamed?

Which condition was inserted?

This can reduce noise compared with line-only diffs.

207. Reviewers should still see textual context

An AST omits some source-level information.

A good interface combines:

structural edit
+
original source text.

208. Comments can matter operationally

Changing:

// temporary workaround; remove after migration

may not change AST at all.

But documentation meaning has changed.

214. Reference pseudocode: token normalization

function normalize_tokens(source):

    tokens =
        lex(source)

    map_identifier = {}
    next_id = 1

    output = []

    for token in tokens:

        if token is comment:
            continue

        if token is identifier:

            if token.value
               not in map_identifier:

                map_identifier[token.value] =
                    "ID_" + next_id

                next_id += 1

            output.append(
                map_identifier[token.value]
            )

        else if token is integer_literal:
            output.append("INT_LITERAL")

        else if token is string_literal:
            output.append("STRING_LITERAL")

        else:
            output.append(token.kind)

    return output

215. This normalization is task-specific

It is appropriate for finding renamed clones.

It is inappropriate when exact constants or names are security-sensitive.

216. Reference pseudocode: token edit similarity

function token_similarity(a, b):

    A =
        normalize_tokens(a)

    B =
        normalize_tokens(b)

    d =
        levenshtein(A, B)

    return
        1 -
        d / max(
            length(A),
            length(B)
        )

The normalization formula is a convention rather than a universal standard.

function ast_feature_vector(tree):

function verify_ast_candidate(
    tree_a,
    tree_b,
    threshold
):

    d =
        tree_edit_distance(
            tree_a,
            tree_b
        )

    norm =
        d /
        max(
          node_count(tree_a),
          node_count(tree_b)

224. Common failure mode: raw Levenshtein is source-code semantics

False.

Raw edit distance measures textual sequence edits.

225. Common failure mode: whitespace difference means code difference

Formatting often has no effect on parsed structure.

226. Common failure mode: comments are always irrelevant

Comments are irrelevant to executable syntax but may matter for provenance, documentation, and review.

227. Common failure mode: variable renaming means different logic

Identifier normalization can reveal structurally identical code beneath renaming.

228. Common failure mode: identifier normalization is always safe

Alias relationships and security-sensitive identifiers can make names important.

229. Common failure mode: literal normalization preserves meaning

Changing one numeric constant can radically alter behavior.

230. Common failure mode: token multiset similarity preserves execution order

Token bags discard ordering.

231. Common failure mode: AST equality means semantic equality

AST nodes can refer to different symbols, types, external functions, or runtime contexts.

232. Common failure mode: similar AST means same behavior

A single changed operator or condition can reverse behavior.

233. Common failure mode: very different ASTs mean different behavior

Iterative and recursive implementations can compute the same function.

234. Common failure mode: tree edit distance understands algebra

Standard ordered-tree distance does not automatically know that some operators are commutative or associative.

235. Common failure mode: GumTree computes exact classical tree edit distance

GumTree is a source-code differencing algorithm designed to infer useful AST mappings and edit scripts including moves.

236. Common failure mode: Deckard is exact AST edit distance

Deckard uses structural vectors and similarity clustering.

237. Common failure mode: MOSS proves plagiarism

MOSS itself explicitly warns against this interpretation.

It detects suspicious similarity that requires human evaluation.

238. Common failure mode: code clone means illegal copying

A clone is a software similarity relationship, not a legal conclusion.

239. Common failure mode: Type-4 clone has one universal formal definition

Semantic clone terminology varies by benchmark and research tradition.

240. Common failure mode: high aggregate similarity proves safety

One tiny malicious difference can matter more than thousands of identical lines.

241. Common failure mode: low aggregate similarity proves unrelated functionality

Alternative algorithms can implement the same behavior.

242. Common failure mode: test agreement proves universal equivalence

Tests cover observed cases, not all possible execution states.

243. Common failure mode: embedding similarity is semantic proof

Embeddings are learned statistical representations.

244. Common failure mode: same embedding neighborhood means copied code

Models can place independently written solutions to the same problem near one another.

245. Common failure mode: exact text match proves direct copying

Both fragments may originate from a standard template or common third-party source.

246. Common failure mode: earliest observed repository proves authorship

Earlier unseen or private sources may exist.

247. Common failure mode: all duplicate code should be refactored

Duplication can sometimes be intentional and safer than premature abstraction.

248. Common failure mode: all ASTs are comparable across parsers

Parser representations and grammar versions differ.

249. Common failure mode: parsing source once represents every build

Preprocessor options and language configuration can produce different programs.

250. Common failure mode: generated code clones indicate developer copying

Generators naturally produce repeated structures.

251. Common failure mode: scalar similarity is sufficient for review

Reviewers need localization and edit explanations.

252. Common failure mode: one threshold works for every fragment size

Short fragments have much higher accidental similarity rates.

253. Common failure mode: one threshold works across languages

Syntax density, token distributions, and parser representations differ.

268. Final interpretation

Source-code similarity begins as a sequence-comparison problem but quickly becomes a representation problem.

At raw character level, Levenshtein distance measures literal textual editing. Tokenization removes formatting noise and treats identifiers or operators as lexical units. Identifier and literal normalization make the detector invariant to selected Type-2 clone transformations. Fingerprinting and inverted indexes make similarity retrieval scalable across massive code corpora.

Abstract syntax trees move the comparison from lexical order toward syntactic hierarchy. Tree edit distance provides a mathematically defined way to compare ordered labeled trees using node edits. The Zhang-Shasha family establishes a foundational exact formulation. Systems such as Deckard approximate structural relationships through AST-derived vectors for scalable clone search. NiCad demonstrates that parser-assisted normalization can make relatively simple comparison methods highly effective. SourcererCC shows how indexing and filtering turn token similarity into a Big Code retrieval problem.

Source differencing adds another objective. GumTree is not merely an AST version of character Levenshtein distance: it constructs mappings and edit scripts intended to represent software evolution, including moved code. A mathematically minimum tree edit script and the edit sequence that best represents developer intent need not be the same.

The boundary becomes even more important with semantic clones. Two structurally different programs can implement the same function. Two nearly identical programs can differ by one negation, constant, permission, API call, or condition and therefore behave radically differently. Moving from ASTs toward control flow, data flow, execution behavior, and learned code representations increases the ability to detect deeper relationships but also makes similarity increasingly model-dependent.

The strongest practical architecture therefore uses multiple layers. Cheap textual or token fingerprints retrieve candidates. Control/data-flow features or learned models can extend recall toward weaker syntactic and functional similarity. The final interpretation remains task-specific and, for high-consequence decisions, should preserve inspectable evidence rather than collapse everything into one similarity score.

Levenshtein distance is most valuable here not because every program should be flattened into a string, but because edit distance supplies the foundational idea: define a representation, define allowed transformations, assign costs, and ask for the minimum transformation. Moving from strings to source tokens, trees, graphs, and program behavior shows both the power and the limit of that idea.
