Edit Distance vs Set, Vector, and N-Gram Similarity: Jaccard, Cosine, Q-Grams, and Retrieval Tradeoffs

Edit Distance vs Set, Vector, and N-Gram Similarity

Levenshtein distance, Jaccard similarity, cosine similarity, and n-gram or q-gram similarity are often used interchangeably in fuzzy matching systems, yet they measure fundamentally different geometric relationships.

The difference begins before any formula is evaluated.

Levenshtein:
string
->
ordered sequence

Jaccard:
object
->
set of features

Cosine:
object
->
weighted vector

q-gram similarity:
string
->
overlapping local substrings
->
set, multiset, or vector.

Once a string is converted from an ordered sequence into a set or vector of features, some information is intentionally discarded. That loss can make similarity dramatically more robust to reordering, long documents, and large-scale retrieval—but it can also collapse strings whose sequence structure is crucial.

Consider:

ABCD
BCDA.

Levenshtein sees a sequence shift that requires edits.

A character-set representation sees:

{A,B,C,D}
=
{B,C,D,A}

and therefore reports perfect set similarity.

Neither answer is universally correct.

They answer different questions.

The central principle of this comparison is:

changing the representation
changes the neighborhood geometry.

This article develops that principle from first principles. It compares Levenshtein distance with Jaccard and Dice set similarity, multiset overlap, cosine similarity, term-frequency and TF-IDF vectors, character n-grams, q-gram profiles, MinHash-style sketches, and scalable filter-and-verify architectures. Particular attention is given to the mathematical relationship between q-gram distance and edit distance, including Ukkonen's q-gram bound.

1. The four major representation families

Representation Preserves global order? Preserves multiplicity? Typical comparison
Sequence Yes Yes Levenshtein / alignment
Set No No Jaccard / Dice
Vector / bag Usually no Yes or weighted Cosine / vector distance
q-gram profile Local order only Optional Jaccard / Dice / cosine / L1

Suppose:

S = "banana".

Possible representations include:

character sequence:
[b,a,n,a,n,a]

character set:
{a,b,n}

character-count vector:
a:3
b:1
n:2

2-gram sequence:
ba
an
na
an
na

2-gram set:
{ba,an,na}

2-gram multiset:
ba:1
an:2
na:2.

3. Every representation answers a different question

Character sequence asks:

How can one ordered character sequence
be transformed into another?

Character set asks:

Which character types occur
in both objects?

Character-count vector asks:

Are their symbol-frequency profiles similar?

q-grams ask:

Do they share local ordered fragments?

4. More information is not always better

Preserving global order makes Levenshtein highly informative about exact sequence structure.

It also makes the metric sensitive to:

  • block movement;
  • token reordering;
  • long inserted regions;
  • document rearrangement.

5. Discarding information creates invariance

A bag-of-words representation ignores word order.

That is useful when:

word ordering changes
but topic remains the same.

It is disastrous when:

word ordering determines meaning.

6. There is no free invariance

ignore a distinction
->
gain robustness to that distinction

but also

lose ability to detect
when that distinction matters.

7. Levenshtein's sequence geometry

Classic Levenshtein distance permits:

insertion

deletion

substitution.

For:

X = x1...xm

Y = y1...yn,

the recurrence is:

D(i,j)
=
min(
 D(i-1,j) + 1,
 D(i,j-1) + 1,
 D(i-1,j-1) + [xi != yj]
).

8. Levenshtein preserves complete sequence order

The algorithm searches for an optimal monotone alignment between the two symbol sequences.

Characters cannot simply be rearranged for free.

9. Example: block reordering

X:
ABCXYZ

Y:
XYZABC.

The symbol inventories are identical.

But the sequence order differs strongly.

10. Character-set similarity sees identity

set(X)
=
{A,B,C,X,Y,Z}

set(Y)
=
{A,B,C,X,Y,Z}.

Therefore:

Jaccard = 1.

11. Levenshtein does not

Moving the block:

ABC

to the end is not one primitive edit.

It must be represented using deletions, insertions, or substitutions.

12. This illustrates representation mismatch, not algorithm error

If block order matters, Levenshtein is more informative.

If the application only cares which symbols occur, the set model may be more appropriate.

13. Set representation

Map an object X to a finite set of features:

F(X).

Features may be:

  • characters;
  • words;
  • q-grams;
  • tokens;
  • attributes;
  • document shingles.

14. Jaccard similarity

For sets:

A
and
B,

define:

J(A,B)
=
|A ∩ B|
/
|A ∪ B|.

15. Jaccard range

0 <= J <= 1.

With:

J = 1

for identical sets and:

J = 0

for disjoint nonempty sets.

16. Jaccard distance

A corresponding set distance is:

dJ(A,B)
=
1 - J(A,B).

For finite sets, Jaccard distance is a mathematical metric.

17. Jaccard deliberately ignores duplicate features

Consider:

X:
red red red blue

Y:
red blue.

As sets:

A = {red,blue}

B = {red,blue}.

Therefore:

J = 1.

18. Frequency information disappeared

The first object contains:

red x3

while the second contains:

red x1.

Set representation intentionally discards that difference.

19. This can be useful for presence/absence data

If the question is:

Which feature types occur?

multiplicity may be irrelevant.

20. It can be disastrous for behavioral counts

For log events:

RETRY x3

and:

RETRY x300000

should often not be considered identical.

21. Dice similarity

For sets:

Dice(A,B)
=
2|A ∩ B|
/
(|A|+|B|).

22. Historical Dice coefficient

Lee R. Dice's 1945 ecological association paper is one of the foundational sources for this overlap form.

See Dice, 1945.

23. Jaccard and Dice contain the same ordering information for fixed representations

Given:

J
=
|A∩B|/|A∪B|,

Dice is:

D
=
2J
/
(1+J).

Conversely:

J
=
D
/
(2-D).

24. Therefore they rank pairs identically when computed from the same two sets

The numerical scales differ.

The underlying intersection/union information does not.

25. Do not compare raw thresholds directly

Jaccard >= 0.8

and:

Dice >= 0.8

are not equivalent acceptance rules.

26. Convert thresholds analytically if necessary

For example, if:

J = 0.8,

then:

Dice
=
1.6 / 1.8
≈
0.8889.

27. Containment differs from symmetric resemblance

Suppose:

A

is a short set of features and:

A ⊂ B

where B is much larger.

Jaccard can be low because the union is dominated by B.

28. Containment coefficient

An asymmetric measure can be:

C(A,B)
=
|A ∩ B|
/
|A|.

This asks:

How much of A
is contained in B?

29. Broder's document resemblance and containment

Andrei Broder formalized resemblance and containment for near-duplicate document detection using shingle sets and sampling.

See On the Resemblance and Containment of Documents.

30. Symmetry matters

J(A,B)
=
J(B,A).

But:

C(A,B)

need not equal:

C(B,A).

31. Containment is useful for plagiarism or inclusion-style questions

A short document can be almost completely contained in a much larger document even though their symmetric Jaccard resemblance is modest.

32. This is analogous to full-string versus substring matching

Full-string edit distance asks whether two entire strings are close.

Containment asks whether most of one representation occurs inside another.

33. A similarity formula must match the query direction

Do not use symmetric resemblance when the true question is:

Is A contained in B?

34. Multisets

A multiset retains feature multiplicity.

Let:

c_A(g)

be the number of occurrences of feature g in object A.

35. Multiset intersection count

|A ∩ B|_multi
=
Σ_g
min(
 c_A(g),
 c_B(g)
).

36. Multiset union count

|A ∪ B|_multi
=
Σ_g
max(
 c_A(g),
 c_B(g)
).

37. Multiset Jaccard

J_multi(A,B)
=
Σ_g min(c_A(g),c_B(g))
/
Σ_g max(c_A(g),c_B(g)).

38. This distinguishes repeated features

For:

X:
red red red blue

Y:
red blue,

multiset intersection has size:

2

and multiset union:

4.

Therefore:

J_multi = 0.5.

39. Same representation, different similarity objective

Even after choosing q-grams, for example, one must decide:

set?

multiset?

weighted vector?

40. Vector representation

Choose a feature vocabulary:

V
=
{f1,f2,...,fd}.

Represent object X as:

x
=
(x1,x2,...,xd)

where each coordinate stores a feature weight.

41. Binary vectors

x_i =
1 if feature i occurs
0 otherwise.

This is essentially a set representation written algebraically.

42. Count vectors

x_i
=
number of times feature i occurs.

This preserves multiplicity.

43. Weighted vectors

Coordinates can instead store:

  • normalized frequency;
  • TF-IDF;
  • business importance;
  • learned weights.

44. Vector-space retrieval

Salton, Wong, and Yang's 1975 work is a foundational treatment of vector-space representations for automatic indexing.

See A Vector Space Model for Automatic Indexing.

45. Cosine similarity

For nonzero vectors:

x
and
y,

define:

cos(x,y)
=
x · y
/
(||x||_2 ||y||_2).

46. Cosine compares direction rather than raw magnitude

If:

y
=
c x

for any:

c > 0,

then:

cos(x,y)
=
1.

47. This can be extremely useful

Suppose one document contains roughly the same term proportions as another but is twice as long.

Cosine can still regard their distributions as nearly identical.

48. It can also deliberately ignore major absolute-count differences

If:

X =
[1,2,3]

Y =
[100,200,300],

then:

cos(X,Y)
=
1.

49. Levenshtein would not behave that way on repeated sequences

If one textual sequence is literally repeated many times, edit distance grows with the additional material.

50. Cosine therefore answers a different question

Are these feature distributions
pointing in similar directions?

not:

How many edits separate
the underlying sequences?

51. Binary cosine

For binary feature vectors corresponding to sets A and B:

cos(A,B)
=
|A ∩ B|
/
sqrt(
 |A||B|
).

52. Binary cosine and Jaccard differ in normalization

Jaccard denominator:

|A ∪ B|.

Binary cosine denominator:

sqrt(
 |A||B|
).

53. Therefore they can rank candidate pairs differently

Especially when feature-set sizes differ substantially.

54. Cosine similarity is not itself a metric distance

The commonly used:

1 - cosine

should not automatically be assumed to satisfy the triangle inequality.

55. Angular distance is a different construction

For appropriate nonzero vectors one can use the angle:

θ
=
arccos(
 cosine(x,y)
).

This has different mathematical properties from:

1 - cosine.

56. Again, API words can be misleading

A library function named:

cosine_distance

may simply return:

1 - cosine_similarity.

Inspect the definition before relying on metric geometry.

57. Term frequency

For a document d and term t:

tf(t,d)

represents how often t occurs in d, possibly after normalization or transformation.

58. Raw term counts overvalue ubiquitous words

Words appearing in nearly every document often provide little discrimination.

59. Inverse document frequency

A common form is:

idf(t)
=
log(
 N / df(t)
)

where:

N
=
number of documents

df(t)
=
number of documents
containing t.

60. Spärck Jones and term specificity

Karen Spärck Jones' influential 1972 work argued for statistically interpreting term specificity using collection frequency.

See A Statistical Interpretation of Term Specificity and Its Application in Retrieval.

61. TF-IDF

A simple weighting scheme is:

w(t,d)
=
tf(t,d)
*
idf(t).

62. Salton and Buckley

Salton and Buckley's 1988 study analyzed term-weighting approaches for automatic text retrieval.

See Term-weighting approaches in automatic text retrieval.

63. TF-IDF changes what overlap means

Sharing:

the

can contribute very little.

Sharing a rare technical term can contribute substantially more.

64. Levenshtein has no corpus frequency model

Every matching character is simply part of the alignment.

It does not know whether that character or token is rare across a collection.

65. Corpus-aware weighting is especially useful for retrieval

The discriminative value of a feature depends partly on:

how often everyone else
contains it.

66. Pairwise geometry and corpus statistics are separate layers

A pairwise edit score has no knowledge of the rest of the database.

A TF-IDF vector explicitly does.

67. Vector representation can use character n-grams too

TF-IDF is not restricted to words.

Features can be:

character 2-grams

character 3-grams

word n-grams

tokens.

68. This creates hybrid systems

For example:

string
->
character 3-gram TF-IDF vector
->
cosine similarity.

This is very different from character-level Levenshtein.

69. N-gram definition

A contiguous n-gram is a sequence of n consecutive units.

For character string:

ABCDE

and:

q = 2,

the ordinary bigrams are:

AB
BC
CD
DE.

70. q-gram and n-gram terminology

In approximate string matching literature, the length is frequently written:

q

and the substrings are called:

q-grams.

Conceptually this is the same contiguous fixed-length-fragment idea as character n-grams.

71. Boundary padding

Some systems add sentinel symbols:

##JOHN$$

before extracting q-grams.

72. Padding preserves edge information

Without padding, the first and last characters participate in fewer q-grams.

73. Padding changes the representation

Therefore two implementations can produce different q-gram similarity scores even with the same:

q.

74. Always document boundary policy

Possible choices include:

  • no padding;
  • one start/end marker;
  • q-1 boundary symbols.

75. q-gram set

For:

BANANA

with:

q=2,

the sequence of q-grams is:

BA
AN
NA
AN
NA.

The unique set is:

{BA,AN,NA}.

76. q-gram multiset

Multiplicity is:

BA:1
AN:2
NA:2.

77. q-gram profile vector

For every possible q-gram g, define:

P_q(S)[g]
=
number of occurrences
of g in S.

78. This converts a string into a high-dimensional sparse vector

If the alphabet size is:

|Σ| = σ,

there are up to:

σ^q

possible q-gram coordinates.

79. Actual profile is usually sparse

A string of length n contains only:

n-q+1

ordinary q-gram positions before boundary padding.

80. q-gram representation preserves local order

The bigram:

AB

distinguishes:

A followed by B

from:

B followed by A.

81. It does not preserve complete global order

Different strings can have identical q-gram profiles.

82. Simple collision example

For:

q = 2

compare:

ABA

and:

BAB.

The 2-gram multisets are:

ABA:
AB, BA

BAB:
BA, AB.

Therefore their 2-gram count profiles are identical.

83. q-gram profile distance can therefore be zero for different strings

d_q(
 "ABA",
 "BAB"
)
=
0

under count-profile L1 distance.

84. This is impossible for true Levenshtein metric identity

Classic Levenshtein satisfies:

dL(X,Y)=0
iff
X=Y.

85. q-gram profile distance is therefore a pseudometric on strings

It is a true metric on the q-gram count vectors themselves.

But the mapping:

string
->
q-gram profile

is not injective.

86. This distinction is mathematically important

A distance can be perfectly valid in feature space while losing identity in the original object space.

87. q-gram L1 distance

Define:

d_q(X,Y)
=
Σ_g
|
P_q(X)[g]
-
P_q(Y)[g]
|.

88. This is Manhattan distance between q-gram profiles

It measures how much q-gram multiplicity must change.

89. Ukkonen's q-gram work

Esko Ukkonen's 1992 paper studied approximate string matching using q-grams and showed how q-gram distances can provide lower bounds useful for edit-distance matching.

See Approximate String-Matching with q-Grams and Maximal Matches.

90. q-gram lemma

For unit-cost edit distance:

d_q(X,Y)
<=
2q
*
d_edit(X,Y).

91. Rearranging gives a lower bound

d_edit(X,Y)
>=
d_q(X,Y)
/
(2q).

92. Why one edit affects only local q-grams

A substitution at one character can alter only q-grams whose windows cover that position.

At most approximately:

q

old q-grams disappear and:

q

new q-grams appear.

93. Hence at most 2q profile-count change

This yields the intuition behind:

d_q
<=
2q d_edit.

94. Insertions and deletions also have local q-gram effects

Although they shift character positions, most q-grams far from the edit remain textually identical.

95. This is a deep difference from positional Hamming comparison

One insertion can misalign every later character position under Hamming.

q-gram overlap remains mostly local.

96. q-gram distance is therefore useful as an edit-distance filter

If:

d_q(X,Y)
>
2qk,

then:

d_edit(X,Y)
>
k.

97. Such a candidate can be safely rejected

For the assumptions of the bound, this is a lossless rejection with respect to the edit-distance threshold.

98. This creates filter-and-verify architecture

candidate strings
      |
      v
cheap q-gram filter
      |
      +---- impossible candidate
      |          |
      |          v
      |        reject
      |
      v
surviving candidates
      |
      v
exact Levenshtein
      |
      v
final answer.

99. Here q-grams are NOT replacing edit distance

They accelerate it.

This is one of the most important distinctions in the entire comparison.

100. Alternative use: q-grams as the final similarity representation

A system may instead decide:

q-gram overlap itself
is the desired similarity.

Then there is no exact edit verifier.

101. These are two fundamentally different architectures

ARCHITECTURE A:
q-grams as approximation/filter
for edit distance

ARCHITECTURE B:
q-grams as final representation.

102. The same preprocessing can therefore serve two different semantics

This is why implementation descriptions must state the final decision rule.

103. Ukkonen's q-gram distance can be computed much more cheaply than full pairwise dynamic programming in suitable representations

This allows q-gram profiles to screen candidate pairs before expensive verification.

104. q-gram filtering is a core scalable-string technique

The broader algorithmic theory is developed in indexing and filtering for edit distance.

105. Approximate string joins

Gravano, Ipeirotis, Jagadish, Koudas, Muthukrishnan, and Srivastava developed database techniques based on positional q-grams for approximate string joins.

See Approximate String Joins in a Database (Almost) for Free.

106. Their architecture is conceptually filter-and-verify

Cheap relational/q-gram filtering generates candidate string pairs.

An expensive edit-distance predicate verifies surviving candidates.

107. Positional q-grams contain more information than plain q-gram sets

Instead of storing only:

"abc"

store:

(position,
 qgram).

108. Position can strengthen filtering

If an edit threshold is small, corresponding q-grams cannot drift arbitrarily far in position.

109. But positional representation becomes more order-sensitive

Once again:

more information
=
more discrimination
+
less invariance.

110. Choice of q is critical

Small q and large q behave differently.

111. q = 1

Features are single symbols.

Almost all sequence order is lost.

112. Larger q preserves more local structure

For:

q = 4,

a match requires four consecutive symbols to agree.

113. Larger q improves feature discrimination

Long grams occur less frequently by chance.

114. Larger q is also more brittle to edits

One character substitution can destroy several overlapping grams.

115. Example

X:
ABCDEF

Y:
ABCXDEF.

Levenshtein:

dL = 1.

116. 3-grams of X

ABC
BCD
CDE
DEF.

117. 3-grams of Y

ABC
BCX
CXD
XDE
DEF.

118. Only two ordinary 3-gram types overlap

ABC
DEF.

119. Set Jaccard is therefore

2
/
(4 + 5 - 2)

=
2/7

≈
0.286.

120. One edit can therefore create surprisingly low q-gram Jaccard on short strings

This is not a contradiction.

The q-gram representation amplified the local disruption because several overlapping windows were affected.

121. Smaller q would be less brittle

But would produce:

  • more common features;
  • larger candidate sets;
  • more collisions.

122. q is a bias-discrimination parameter

small q
->
high tolerance
+
weak discrimination

large q
->
strong discrimination
+
high edit sensitivity.

123. There is no universal optimal q

It depends on:

  • string length;
  • alphabet;
  • expected edit rate;
  • corpus size;
  • language;
  • memory budget.

124. Short strings constrain q severely

If:

|S| = 5

and:

q = 5,

there is only one ordinary q-gram.

One edit can destroy the only feature.

125. Long strings support larger grams

But retrieval-scale vocabulary can become huge.

126. Feature vocabulary grows exponentially with q

In principle:

|Σ|^q.

Sparse storage is therefore essential.

127. Character alphabet size matters

For DNA:

|Σ| ≈ 4

for canonical nucleotides.

For Unicode text, the conceptual symbol space is dramatically larger.

128. Normalization matters before q-gram generation

Case differences, Unicode normalization, punctuation, and tokenization alter every downstream gram.

129. q-gram representation inherits representation mistakes

If UTF-8 bytes are accidentally treated as characters, n-grams can split multi-byte characters.

130. Grapheme-safe n-grams

One can generate grams over:

extended grapheme clusters

rather than code points or bytes.

See Unicode and grapheme-safe Levenshtein for the underlying segmentation distinction.

131. Word n-grams

N-grams need not be characters.

For:

the quick brown fox

word bigrams are:

the quick

quick brown

brown fox.

132. Word n-grams preserve local phrase order

They are often useful for:

  • near-duplicate documents;
  • plagiarism detection;
  • phrase retrieval;
  • text classification.

133. Character and word n-grams respond differently to spelling errors

One typo destroys several character grams but can also convert an entire word token into a different word, destroying word-level n-grams around it.

134. Tokenization therefore determines robustness

Again:

representation first,
metric second.

135. Set q-grams versus multiset q-grams

Consider:

AAAAAA.

For:

q=2,

every gram is:

AA.

136. Set representation contains one feature

{AA}.

137. Multiset representation preserves five occurrences

AA:5.

138. This difference matters for repetitive strings

Set Jaccard may consider:

AAAA

and:

AAAAAAAAAAAAAAAA

identical at the unique 2-gram level.

139. Count-vector cosine gives another behavior

If both vectors contain only coordinate:

AA

with positive counts, the vectors are scalar multiples.

Therefore:

293. Reference pseudocode: Jaccard

function jaccard(A, B):

    if A and B are empty:
        return 1

    intersection =
        size(A intersect B)

    union =
        size(A union B)

    return
        intersection / union

294. Reference pseudocode: Dice

function dice(A, B):

    if A and B are empty:
        return 1

    common =
        size(A intersect B)

    return
        2 * common
        /
        (size(A) + size(B))

295. Reference pseudocode: multiset Jaccard

function multiset_jaccard(countA,
                          countB):

    intersection = 0
    union = 0

    for each feature g
        in keys(A) union keys(B):

        intersection +=
            min(
              countA[g],
              countB[g]
            )

        union +=
            max(
              countA[g],
              countB[g]
            )

    if union == 0:
        return 1

    return
        intersection / union

296. Reference pseudocode: cosine

function cosine(x, y):

    dot = 0
    norm_x = 0
    norm_y = 0

    for feature g:

        dot +=
            x[g] * y[g]

        norm_x +=
            x[g]^2

        norm_y +=
            y[g]^2

    if norm_x == 0
       or norm_y == 0:
        handle zero-vector policy

    return
        dot
        /
        (
          sqrt(norm_x)
          *
          sqrt(norm_y)
        )

function qgrams(S, q):

    grams = []

    if q <= 0:
        error

    if len(S) < q:
        return grams

    for i in 0..len(S)-q:

        grams.append(
            S[i : i+q]
        )

    return grams

function qgram_profile(S, q):

    profile =
        empty frequency map

    for g in qgrams(S, q):

300. Reference pseudocode: q-gram L1 distance

function qgram_distance(X, Y, q):

    px =
        qgram_profile(X,q)

    py =
        qgram_profile(Y,q)

    distance = 0

    for g in
        keys(px) union keys(py):

        distance +=
            abs(
              px[g] - py[g]
            )

    return distance

Sequence geometry defines the final answer.

337. This is often preferable to forcing one measure to do everything

Retrieval and verification have different optimization requirements.

Unlike the relationship between some nested edit models, there is no general theorem saying:

Pair A can have:

but:

than pair B.

341. This happens because neighborhoods have different shapes

Levenshtein balls contain strings reachable by bounded edit operations.

Jaccard neighborhoods contain sets with sufficient intersection relative to union.

Cosine neighborhoods contain vectors with similar direction.

342. Geometric language is useful

Each measure induces a different notion of:

  • near;
  • far;
  • neighbor;
  • cluster;
  • outlier.

Clustering the same documents with:

edit distance

versus:

cosine TF-IDF

can produce entirely different groupings.

344. Neither clustering is intrinsically “correct”

One may cluster by textual form.

The other may cluster by vocabulary distribution.

345. A similarity measure encodes the task's invariances

Before implementation, explicitly answer:

Should word order matter?

Should repetition matter?

Should document length matter?

Should block movement matter?

Should rare terms matter more?

Should one insertion be local?

Should containment be asymmetric?

346. Only then choose representation and metric

This avoids one of the most common engineering mistakes:

choosing a familiar formula
before defining similarity.

348. Final interpretation

The most important distinction between edit distance and set, vector, and n-gram similarity is not the mathematical formula used at the final step. It is the representation of the object before that formula is applied.

Levenshtein distance operates directly on an ordered sequence. Every insertion, deletion, and substitution participates in a global alignment, so long-range order remains part of the geometry. This is ideal when those edits genuinely define the differences the application cares about.

Jaccard and Dice instead compare sets of features. They intentionally forget feature multiplicity and order. This makes them robust to rearrangement and useful for overlap-oriented problems, but two distinct strings can become identical after set conversion. Their score means:

shared feature types
relative to feature inventory,

not:

minimum sequence transformation.

Vectors retain more information. Count vectors preserve multiplicity, TF-IDF vectors incorporate corpus-level rarity, and cosine similarity compares the direction of weighted feature profiles rather than absolute sequence length. This makes vector-space methods particularly powerful for information retrieval, where a long document and a short document can discuss the same subject with similar feature proportions.

Character and token n-grams occupy an important middle ground. They discard global order while preserving local adjacency. This allows strings and documents to survive local edits, movement, and partial rearrangement more gracefully than full sequence alignment, while still retaining substantially more structure than unordered sets of individual characters or words.

But “n-gram similarity” is not one metric. A q-gram representation can be converted into:

unique set
->
Jaccard

multiset
->
multiset Jaccard

count vector
->
cosine

count vector
->
L1 q-gram distance

weighted vector
->
TF-IDF cosine.

These systems can rank the same candidate pairs differently because they preserve different information.

Ukkonen's q-gram result reveals an especially important relationship with edit distance. If d_q is the L1 distance between q-gram count profiles and d_edit is unit-cost edit distance, then:

d_q(X,Y)
<=
2q d_edit(X,Y).

Therefore:

d_edit(X,Y)
>=
d_q(X,Y)/(2q).

This allows q-grams to serve not merely as an alternative similarity representation but as a computational filter for exact edit-distance search. A candidate whose q-gram lower bound already exceeds the target threshold can be rejected before dynamic programming is run.

That leads to one of the most important architectures in large-scale fuzzy retrieval:

feature index
->
cheap candidate filtering
->
exact sequence verification.

In such a pipeline, q-grams provide scalability while Levenshtein retains final semantics. The two techniques are collaborators rather than competitors.

The practical rule is therefore:

Use Levenshtein
when exact ordered edit structure
is the desired geometry.

Use Jaccard or Dice
when feature presence matters
more than order or frequency.

Use multiset/vector methods
when repetition matters.

Use cosine and TF-IDF
when relative weighted feature distribution
is central.

Use q-grams
when local sequence structure
is useful but complete global alignment
is too brittle or too expensive.

Use q-gram filtering plus Levenshtein
when exact edit-distance semantics
must scale to large collections.

The deeper rule is even more general:

do not ask which similarity formula
is best

until you have decided
which information
you are willing to discard.

That decision determines the geometry long before the final similarity score is calculated.
