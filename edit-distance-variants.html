Edit Distance Variants

Edit distance is not a single immutable formula. It is a family of optimization problems defined by the operations that may transform one sequence into another, the costs assigned to those operations, the representation of the sequence itself, and the way the resulting transformation cost is interpreted.

The familiar Levenshtein distance is one particularly important member of this family: insertion, deletion, and substitution are permitted, each with unit cost. But changing even one assumption produces a different mathematical object. Removing insertions and deletions gives Hamming distance. Removing substitution produces insertion-deletion distance and a direct relationship with longest common subsequences. Adding adjacent transposition leads toward Damerau–Levenshtein distance. Assigning nonuniform costs gives weighted edit distance. Changing gap costs produces sequence-alignment models. Normalizing the score changes its scale and can change its metric properties. Replacing characters with tokens, grapheme clusters, trees, or graphs changes the underlying domain.

Understanding these distinctions is essential because two algorithms can both be called “edit distance” while solving meaningfully different problems.

A General Mathematical Definition

Let:

x ∈ Σ*
y ∈ Σ*

be finite sequences over an alphabet Σ.

Let:

Ω

be a collection of permitted edit operations.

Each operation:

o ∈ Ω

has nonnegative cost:

w(o) ≥ 0

An edit script:

E =
(o₁,o₂,...,o_r)

transforms:

x → y

when applying its operations sequentially converts x into y.

The generalized edit cost is:

d_Ω,w(x,y)
=
min over edit scripts E transforming x into y
Σ_(o∈E) w(o)

This one formulation contains many familiar distances.

A variant can therefore arise by changing:

Ω
=
allowed operations

w
=
operation costs

Σ
=
sequence alphabet / representation

boundary conditions
=
which prefixes or suffixes may be ignored

normalization
=
how the raw transformation cost is scaled

object domain
=
strings, tokens, trees, graphs, sequences, etc.

The Six Major Axes of Edit-Distance Variation

Axis Question Examples
Operation set What transformations are permitted? Insert, delete, substitute, transpose, block replace
Cost model What does each operation cost? Unit, weighted, probabilistic, context-dependent
Sequence unit What counts as one element? Byte, code point, grapheme, token, residue
Boundary model Must complete sequences be aligned? Global, semiglobal, substring, local
Score transformation How is raw cost interpreted? Raw distance, normalized distance, similarity
Object structure Are the objects linear strings? Strings, trees, graphs

Classical Levenshtein Distance

The standard Levenshtein operation set is:

Ω_L =
{
    insertion,
    deletion,
    substitution
}

with:

cost(insert)     = 1
cost(delete)     = 1
cost(substitute) = 1
cost(match)      = 0

Its dynamic-programming recurrence is:

D[i][j]
=
min(
    D[i-1][j] + 1,
    D[i][j-1] + 1,
    D[i-1][j-1] + [x_i ≠ y_j]
)

where:

[condition]
=
1 if condition is true
0 otherwise

with:

D[i][0] = i
D[0][j] = j

The resulting value is:

d_L(x,y) = D[|x|][|y|]

For additional foundations, see Edit Distance and Edit Operations and Edit Scripts.

Historical Terminology: "Reversal" Did Not Mean Transposition

A historical terminology trap is worth making explicit.

Vladimir Levenshtein's original coding-theory work discussed binary:

deletions
insertions
reversals

In that context, a binary “reversal” referred to:

0 → 1
or
1 → 0

what modern string-algorithm terminology normally calls a substitution or symbol error.

It should not be confused with:

ab → ba

which is an adjacent transposition and belongs to the Damerau family of edit models.

This historical distinction prevents an important conceptual error: classical Levenshtein distance does not contain adjacent transposition as a primitive edit.

Weighted Edit Distance

The most direct generalization replaces uniform unit costs with symbol-dependent costs.

Define:

c_del(a)
c_ins(b)
c_sub(a,b)

Then:

D[i][j]
=
min(
    D[i-1][j]
        + c_del(x_i),

    D[i][j-1]
        + c_ins(y_j),

    D[i-1][j-1]
        + c_sub(x_i,y_j)
)

The boundary conditions become:

D[i][0]
=
Σ_(r=1)^i c_del(x_r)

D[0][j]
=
Σ_(r=1)^j c_ins(y_r)

Example

Suppose a keyboard model assigns:

substitute(i,o) = 0.25
substitute(i,z) = 1.00

because i and o are adjacent keys.

Then:

d("kit","kot")

can be smaller than:

d("kit","kzt")

even though both pairs require one substitution under unit-cost Levenshtein distance.

This model is treated in depth in Weighted Levenshtein Distance.

The Effective Substitution Cost

A subtle property of weighted models is that the direct substitution cost is not necessarily the cost ultimately paid by the edit distance.

Suppose:

c_sub(a,b) = 10

c_del(a) = 1
c_ins(b) = 1

Then the optimal transformation:

a → b

will not use the direct substitution.

It can instead use:

delete a
insert b

for total cost:

2

Therefore the effective transformation cost is:

min(
    c_sub(a,b),
    c_del(a) + c_ins(b)
)

when no other operation offers an even cheaper route.

The edit distance is a shortest-path cost over edit scripts, not necessarily the value written in one entry of a cost matrix.

Symmetric and Asymmetric Edit Distance

Classical Levenshtein distance satisfies:

d(x,y) = d(y,x)

Weighted edit cost need not.

Suppose:

insert(a) = 1
delete(a) = 4

Then transforming:

"" → "a"

costs:

1

while:

"a" → ""

costs:

4

The resulting function is directed:

d(x,y) ≠ d(y,x)

Such a score may still be useful—for example when modeling an asymmetric noisy channel— but it is not a metric in the usual symmetric sense.

Metric Conditions Matter

A function:

d : X × X → ℝ

is a metric when it satisfies:

1. d(x,y) ≥ 0

2. d(x,y) = 0
   iff x = y

3. d(x,y) = d(y,x)

4. d(x,z)
   ≤
   d(x,y) + d(y,z)

Classical unit-cost Levenshtein distance satisfies these conditions.

A generalized edit cost with nonnegative operation costs does not automatically satisfy all of them.

Potential violations include:

  • zero-cost transformations between distinct sequences, which can violate identity of indiscernibles;
  • asymmetric insertion, deletion, or substitution costs;
  • normalizations that do not preserve triangle inequality;
  • restricted edit rules that prevent the required path-composition behavior.

If a still broader formulation allows negative edit costs, even non-negativity is no longer guaranteed and repeated negative-cost cycles can make a shortest-path formulation ill-defined. Such models lie outside the nonnegative-cost definition used above.

Metricity is not merely theoretical. Structures such as BK-trees and other metric indexes rely directly on the triangle inequality for correct pruning.

Hamming Distance

Hamming distance permits only substitutions and requires equal-length sequences.

For:

|x| = |y| = n

define:

d_H(x,y)
=
Σ_(i=1)^n
[x_i ≠ y_i]

Example

x = abcdef
y = abqdez

The differing positions are:

c/q
f/z

therefore:

d_H(x,y) = 2

Why Hamming Distance Is Not Simply "Fast Levenshtein"

Hamming distance solves a different mathematical problem.

Consider:

x = abc
y = bca

Hamming distance is:

3

because all three aligned positions differ.

Levenshtein distance is:

2

because:

abc
→
bc
→
bca

using one deletion and one insertion.

Thus for equal-length strings:

d_L(x,y)
≤
d_H(x,y)

but the difference can be substantial when a short insertion/deletion shift realigns a long suffix.

Complexity of Hamming Distance

A direct implementation requires only one pass:

for i:
    if x[i] != y[i]:
        errors++

so:

Time:
O(n)

Space:
O(1)

Hamming distance therefore belongs to a much simpler computational regime than unrestricted insertion/deletion edit distance.

Insertion-Deletion Distance

Another important simplification removes substitution as a primitive operation.

Allowed operations are only:

insert
delete

with unit cost.

This is often called:

  • insertion-deletion distance;
  • Indel distance;
  • LCS distance in appropriate formulations.

Relationship to the Longest Common Subsequence

Let:

L =
LCS(x,y)

be the length of a longest common subsequence.

To transform x into y using only insertions and deletions:

  1. retain an LCS of length L;
  2. delete the other |x|-L symbols from x;
  3. insert the remaining |y|-L symbols required by y.

Therefore:

d_ID(x,y)
=
|x|
+
|y|
-
2 · LCS(x,y)

Example

x = abc
y = acb

An LCS has length:

2

for example:

ab

or:

ac

Thus:

d_ID(x,y)
=
3 + 3 - 2·2
=
2

Relationship Between Indel and Levenshtein Distance

Every Levenshtein substitution can be simulated by:

one deletion
+
one insertion

Therefore, under unit costs:

d_L(x,y)
≤
d_ID(x,y)
≤
2 d_L(x,y)

The first inequality follows because Levenshtein permits every Indel script plus direct substitutions.

The second follows by replacing every substitution in an optimal Levenshtein script with two Indel operations.

Why Indel Distance Matters

Insertion-deletion distance is fundamental in:

  • coding theory;
  • sequence synchronization;
  • Longest Common Subsequence theory;
  • DNA insertion/deletion channels;
  • document difference algorithms.

It should not be treated as identical to unit-cost Levenshtein distance simply because both allow length-changing edits.

Damerau–Levenshtein Distance

Damerau-style distances add adjacent transposition:

ab → ba

as a primitive operation.

The operation set becomes:

insert
delete
substitute
transpose adjacent symbols

Example

x = abc
y = acb

Standard Levenshtein distance is:

2

because the final two symbols require two substitutions or an equivalent delete/insert script.

With adjacent transposition:

abc
→
acb

costs:

1

This is important for typing-error models because adjacent symbol swaps are common human errors.

See Damerau–Levenshtein Distance for the complete theory.

Optimal String Alignment Distance Is Not Unrestricted Damerau–Levenshtein Distance

One of the most common errors in string-similarity software is labeling the simple transposition recurrence as full Damerau–Levenshtein distance.

The commonly implemented recurrence:

D[i][j]
=
min(
    insertion,
    deletion,
    substitution,
    D[i-2][j-2] + 1
        if
        x_i = y_(j-1)
        and
        x_(i-1) = y_j
)

normally computes the Optimal String Alignment distance, also called a restricted Damerau–Levenshtein distance.

It restricts how substrings can participate in multiple edit operations.

The unrestricted Damerau–Levenshtein problem allows interacting transpositions that this simple recurrence cannot represent correctly.

A Diagnostic Example

Consider:

x = "ca"
y = "abc"

Unrestricted Damerau–Levenshtein can use:

ca
→
ac
→
abc

with:

transpose ca → ac
insert b

for total cost:

2

The restricted Optimal String Alignment formulation gives:

3

because its transposed substring cannot subsequently participate in the same way in another edit.

Optimal String Alignment Is Not a Metric

Consider:

x = "ca"
y = "ac"
z = "abc"

Under Optimal String Alignment:

d(x,y) = 1

because:

ca → ac

is one transposition.

Also:

d(y,z) = 1

because:

ac → abc

is one insertion.

But:

d(x,z) = 3

so:

3
>
1 + 1

and the triangle inequality fails.

This is not merely an academic distinction. A metric index designed for classical Levenshtein or unrestricted metric Damerau–Levenshtein distance cannot automatically be reused with Optimal String Alignment distance.

Generalized Transpositions

Adjacent transposition is only one possible permutation operation.

More general models may permit:

ab → ba

only when symbols are adjacent, or permit:

moving a symbol
swapping distant symbols
moving substrings
reordering blocks

These are different edit models.

Changing from adjacent transposition to arbitrary block movement can radically alter:

  • the dynamic-programming state;
  • metric properties;
  • computational complexity;
  • the interpretation of one edit.

The phrase “edit distance with transpositions” is therefore incomplete unless the permitted transposition operation is specified precisely.

Substring and Block Edit Operations

Classical edit distance operates on one symbol at a time.

A generalized operation can replace a substring:

u

with another substring:

v

at cost:

c(u,v)

Examples include:

"tion" → "sion"
"colour" → "color"
"ph" → "f"

Such operations can better represent linguistic or domain-specific transformations.

A generalized recurrence may need to examine:

D[i-|u|][j-|v|]
+
c(u,v)

for many possible substring pairs.

Gap-Cost Variants

Classical Levenshtein assigns:

cost of deleting ℓ consecutive symbols
=
ℓ

and similarly for insertions.

Many sequence-alignment problems instead use a gap cost:

g(ℓ)

for a complete run of ℓ inserted or deleted symbols.

Linear Gap Cost

g(ℓ) = ℓ

Affine Gap Cost

g(ℓ)
=
g_open
+
(ℓ-1)g_extend

where typically:

g_open > g_extend

Why Affine Gaps Need Additional State

The algorithm must know whether the current operation opens a new gap or extends an existing gap.

A common formulation uses three states:

M[i][j]
=
best alignment ending in
a matched/substituted pair

I_x[i][j]
=
best alignment ending
inside a gap in one sequence

I_y[i][j]
=
best alignment ending
inside a gap in the other sequence

See Sequence Alignment and Gap Models.

Affine-Gap Alignment Is Not Simply Weighted Levenshtein

A symbol-dependent insertion cost such as:

insert(a) = 2

is still local to one symbol.

Affine gap cost depends on whether adjacent insertions or deletions belong to the same run.

cost of current edit
depends on previous edit context

This moves beyond the memoryless edit-operation model used by ordinary weighted Levenshtein distance.

Global Edit Distance

Standard Levenshtein distance is a global sequence comparison.

x[1..m]
→
y[1..n]

Unmatched prefixes or suffixes incur edit costs.

Semiglobal Edit Objectives

Applications sometimes wish to align a complete query against part of another sequence while allowing selected terminal gaps to be free.

query:
    abc

text:
    xxxxxabcxxxxx

A semiglobal formulation can avoid charging for unrelated text outside the aligned query region.

Approximate Substring Matching

A search formulation may ask:

min over substrings y[a..b]
d_L(
    x,
    y[a..b]
)

This is a change in the alignment objective, not necessarily a new edit operation.

The distinction is important in approximate string-matching algorithms and in bit-parallel search methods. See Myers Bit-Vector Algorithm.

Local Alignment Is Not Ordinary Edit Distance

Local sequence alignment searches for the best pair of subsequences:

x[a..b]
and
y[c..d]

rather than requiring either full sequence to be transformed.

It is better understood as a related sequence-alignment objective than as merely another normalization of Levenshtein distance.

Normalized Levenshtein Distance and Similarity

Raw Levenshtein distance measures an absolute edit cost. That value is often appropriate when the application asks:

How many edits separate x and y?

But raw distance is strongly affected by sequence length.

Consider:

d("a","b") = 1

and:

d(
  "internationalization",
  "internationalisation"
)
=
1

The raw edit cost is identical, but one edit represents a much larger relative change in the first pair.

Normalization therefore introduces a second modeling decision:

raw edit cost
+
chosen denominator or path objective
=
normalized edit score

There is no single universal definition of normalized Levenshtein distance. The normalization rule must be stated explicitly.

Post-Normalized Levenshtein Distance

A common family of normalized scores first computes classical Levenshtein distance:

d_L(x,y)

and then divides that already-optimized raw distance by a length-based denominator.

A common definition is:

d_max(x,y)
=
d_L(x,y)
/
max(|x|,|y|)

For nonempty input pairs under ordinary unit-cost Levenshtein distance on the same sequence representation:

0 ≤ d_max(x,y) ≤ 1

with:

0
=
identical sequences

and larger values representing greater relative edit burden. The both-empty case requires an explicit software convention because the formula becomes 0/0.

Normalization Is Not Unique

Different denominators encode different notions of relative error.

Normalization Interpretation Important consequence
d / max(m,n) Error burden relative to the longer sequence Bounded by 1 for ordinary unit-cost Levenshtein; undefined by the raw formula when both lengths are zero
d / min(m,n) Error burden relative to the shorter sequence Can exceed 1; denominator is zero whenever either sequence is empty
2d / (m+n) Symmetric normalization by average length Different scale from max-length normalization; undefined by the raw formula when both sequences are empty
d / reference_length Error burden relative to a designated reference Directional interpretation; may exceed 1 and needs a policy when reference length is zero
Cost per edit-path step Average transformation cost along a path Different optimization problem

Therefore a statement such as:

normalized edit distance = 0.2

is incomplete unless the normalization formula is known.

Zero-Denominator Cases Are Formula-Specific

Different normalization formulas fail on different empty-input cases.

d / max(m,n)

denominator = 0
only when:
m = 0 and n = 0
d / min(m,n)

denominator = 0
when:
m = 0 or n = 0
2d / (m+n)

denominator = 0
only when:
m = 0 and n = 0
d / reference_length

denominator = 0
whenever the designated
reference is empty

A production implementation must therefore define edge-case semantics for the exact formula it uses. It should not rely on accidental language-level division behavior.

For max-length normalized unit-cost Levenshtein similarity, a common explicit convention is:

normalized_distance("", "") = 0

normalized_similarity("", "") = 1

For formulas involving min(m,n) or a designated reference length, the application must state its own behavior when that denominator is zero.

The Numerator and Denominator Must Use the Same Sequence Semantics

The distance numerator and the length denominator should refer to the same underlying sequence representation.

For example, do not silently compute:

distance
on Unicode code points

÷

length
in UTF-16 code units

or:

distance
on grapheme clusters

÷

length
in Unicode code points

Those expressions combine two different sequence spaces. The resulting number can be computed, but its meaning is no longer a coherent normalization of the distance that was measured.

A reproducible definition should therefore specify:

sequence unit
+
edit model
+
raw distance
+
denominator
=
normalized distance semantics

For multilingual text, see Unicode and Grapheme-Safe Levenshtein.

Normalized Levenshtein Similarity

A normalized distance can be converted to a similarity when its scale has been defined appropriately.

For max-length normalized unit-cost Levenshtein distance:

s_max(x,y)
=
1
-
d_L(x,y) / max(|x|,|y|)

for nonempty input pairs, giving:

1
=
identical

0
=
maximum raw Levenshtein distance
relative to the longer sequence

For the both-empty case, the application should use its documented convention rather than evaluate 1 - 0/0.

This is a convenient similarity score, but it is not the original Levenshtein metric.

Levenshtein distance
≠
normalized distance
≠
normalized similarity

Not Every Distance-to-Similarity Transformation Produces a 0–1 Score

The formula:

similarity = 1 - normalized_distance

only behaves as a conventional 0..1 similarity when the normalized distance itself has the intended 0..1 range.

For example:

d / min(m,n)

can exceed 1 when the denominator is nonzero. Therefore:

1 - d/min(m,n)

can become negative.

Likewise, weighted edit distances can exceed the ordinary unit-cost upper bound when insertion, deletion, or substitution costs are larger than 1.

A similarity transformation must therefore be derived from the actual distance range, not copied mechanically from another metric.

Post-Normalization Does Not Change the Optimal Edit Script

If the denominator depends only on the two input sequences and not on the particular edit path, then post-normalization occurs after the raw distance has already been minimized:

find
argmin_P C(P)

then compute

min_P C(P)
/
N(x,y)

The selected edit script is therefore still the raw minimum-cost script. Only its reported score is rescaled.

Normalized Edit Distance of Marzal and Vidal

A deeper formulation optimizes a normalized path objective directly rather than first finding the minimum raw-cost path and dividing afterward.

If an edit path:

P

has total cost:

C(P)

and path length:

L(P)

a normalized path objective can be written conceptually as:

C(P) / L(P)

The desired path is then:

argmin_P
C(P) / L(P)

This need not be the same path as:

argmin_P C(P)

followed by division afterward.

Therefore:

minimum raw edit cost
then normalize

and:

minimum normalized path cost

are distinct optimization problems.

This distinction is important because the phrase normalized edit distance is used for different constructions in technical literature.

Normalization Does Not Automatically Preserve Metricity

One should never assume:

metric distance
        ↓
divide by arbitrary
pair-dependent denominator
        ↓
still a metric

Even when the raw Levenshtein distance satisfies non-negativity, identity, symmetry, and triangle inequality, an arbitrary transformed score does not automatically inherit all those properties.

The particular normalization must be analyzed.

This statement does not mean that every normalized edit-distance construction is nonmetric. Specialized normalized Levenshtein formulations can be designed specifically to satisfy metric properties under stated cost conditions.

This matters when normalized scores are used inside:

  • metric indexes;
  • BK-trees;
  • nearest-neighbor structures;
  • clustering methods;
  • geometric embeddings;
  • algorithms whose pruning proofs require triangle inequality.

Normalized Distance Is Not Probability

Suppose:

normalized distance = 0.2

This does not imply:

80% probability
that x and y represent
the same object

Likewise:

similarity = 0.8

does not automatically mean:

80% confidence
of identity

Normalization changes numerical scale. Probability calibration requires a separate probabilistic or empirical model.

Thresholds Are Formula-Specific

A threshold such as:

normalized distance ≤ 0.2

has meaning only relative to a named formula and sequence representation.

For reproducibility, report:

1. sequence representation
2. allowed edit operations
3. operation costs
4. raw distance definition
5. normalization denominator or path objective
6. zero-denominator policy
7. score direction
8. score range
9. threshold

For example:

unit-cost Levenshtein
over Unicode code points

Levenshtein similarity ≥ 80%

Canonical Interpretation

When this site uses the phrase normalized Levenshtein distance without another model being explicitly named, the safest interpretation is:

+

When path-normalized Marzal–Vidal NED is intended, it should be named separately because it optimizes a different objective.

This distinction keeps:

Probabilistic Edit Models

A noisy-channel model can associate probabilities with operations:

P(delete a)
P(insert b)

A common transformation is:

=

Then minimizing total edit cost corresponds to maximizing the probability of a single edit path when the operation probabilities factor according to the model.

A crucial probabilistic distinction is:

The mathematical model becomes closer to:

  • hidden-state sequence models;

A UTF-8 character may occupy multiple bytes. If edit distance is computed directly on bytes, replacing one user-perceived character can create several byte edits.

Code-Point Distance

Decoding Unicode to code points is better for many tasks but still does not make one code point equal one user-perceived character.

For example:

Without normalization, these canonically equivalent strings have different code-point sequences.

    ↓

x =
[the, quick, brown, fox]

y =
[the, fast, brown, fox]

At token level:

d_L(x,y) = 1

because:

is one token substitution.

At character level, the distance is larger. Neither answer is intrinsically more correct. They represent different sequence models.

Names and language data can be converted into:

  • phonemes;
  • romanized forms;
  • phonetic codes;
  • language-specific normalized units.

Edit distance applied after such a transformation measures differences in the transformed representation rather than the original orthography.

Strings are linear structures. A tree contains hierarchical relationships.

Tree edit distance generalizes edit operations to nodes:

  • vertex deletion;
  • vertex relabeling;
  • edge insertion;
  • edge deletion;

For nonzero smoothing, the resulting objective is generally not identical to classical edit distance and should not automatically be assumed to satisfy metric axioms.

Failure Mode: Changing Costs Without Changing Assumptions

A pairwise weighted dynamic program can be correct while surrounding search/indexing assumptions become invalid.

Changing the distance requires auditing every algorithmic assumption built on top of it.

Failure Mode: Using an Operation That Cannot Represent the Real Error Process

Suppose OCR frequently transforms:

rn → m

A block substitution could model it as one event, while character-level Levenshtein requires a different edit script.

The standard distance is not wrong; it models a different process.

Failure Mode: Confusing Normalization with Calibration

normalized distance = 0.2

does not imply:

80% probability
that the strings represent
the same entity

Normalization changes scale. Calibration requires a separate model.

Failure Mode: Treating a Learned Score as a Metric

d(a,b) = 0.1
d(b,c) = 0.1
d(a,c) = 1.8

violates triangle inequality. The score may still be useful for ranking, but cannot safely drive algorithms that depend on metric geometry.

Failure Mode: Mixing Representation Levels

An index might operate on:

UTF-8 bytes

while the final verifier uses:

Unicode grapheme clusters

A filtering theorem proved in one representation may not remain valid for the other.

How to Specify an Edit-Distance Variant Rigorously

  1. What is the input domain? Strings, bytes, code points, graphemes, tokens, trees, or graphs?
  2. What operations are permitted? Insert, delete, substitute, transpose, block replace, move?
  3. What does each operation cost?
  4. Do costs depend on symbols or context?
  5. Are complete objects aligned globally?
  6. Are terminal gaps free?
  7. Is the output raw or normalized?
  8. If normalized, what exact denominator or path objective is used?
  9. What is the zero-denominator policy?
  10. What sequence unit is used for both distance and length?
  11. What is the score range and direction?
  12. Does the function need to be a metric?
  13. Must the algorithm return only a distance or also an edit script?
  14. Is exact computation required?

Operation Witnesses

Verify an edit script whose cost equals the returned result.

Empty Sequence

For ordinary unit-cost Levenshtein distance:

d("",y) = |y|
d(x,"") = |x|

Identity

Symmetry

d(x,y) = d(y,x)

Triangle Inequality

d(x,z)
≤

Restricted Versus Unrestricted Transposition

"ca"
"abc"

Weighted Substitution Domination

Set substitution cost greater than deletion plus insertion and verify that the composite path is selected.

Unicode Canonical Equivalence

Test normalized and non-normalized forms of accented text to ensure that the implementation matches the intended sequence definition.

Normalized-Score Tests

Include at least:

  • identical non-empty sequences;
  • two empty sequences;
  • one empty and one non-empty sequence;
  • large length imbalance;

Choosing a Variant Is Ultimately Choosing an Error Model

The most important question is not:

Which distance gives
the smallest number?

It is:

Which edit operations correspond
to meaningful changes
in this application?

If adjacent character swaps are genuine one-step errors, Damerau-style distance may be appropriate.

If insertions and deletions represent synchronization errors, Indel distance may be the right object.

If substitutions have highly unequal probabilities, weighted edit distance is more faithful.

If long gaps correspond to one biological event, affine-gap alignment may be better.

If meaning rather than surface form matters, character edit distance may not be the appropriate primary model at all.

Key Facts

Question Answer
Is Levenshtein the only edit distance? No. It is one important member of a broad family.
What defines an edit-distance variant? Operation set, costs, sequence representation, boundaries, normalization, and object domain.
Does classical Levenshtein include transposition? No.
Is Hamming distance a special restricted edit model? It can be viewed that way on equal-length sequences: substitution only.
How is Indel distance related to LCS? d_ID(x,y)=|x|+|y|-2LCS(x,y)
Is Optimal String Alignment full Damerau–Levenshtein? No.
Is Optimal String Alignment a metric? No; triangle inequality can fail.
Are arbitrary weighted edit scores metrics? Not automatically.
Is there one universal normalized Levenshtein formula? No. The denominator or path objective must be stated explicitly.
Is post-normalized Levenshtein the same as Marzal–Vidal NED? No. One normalizes an already-minimized raw cost; the other optimizes a normalized path objective directly.
Does normalization preserve metricity? Not automatically. Some specialized normalized formulations are metrics, but arbitrary normalization must be proved.
Does normalized similarity represent probability? No. Calibration is a separate problem.
Must distance and length use the same sequence unit? Yes, if the normalized score is to have coherent sequence semantics.
Must zero-denominator behavior be defined? Yes. Different formulas encounter zero denominators under different empty-input conditions.
Is bounded edit distance a new distance definition? Usually no; it is a thresholded computational problem.
Are tree and graph edit distances identical to string edit distance? No; they generalize the edit concept to structured objects.

Summary

Edit distance is best understood as a general optimization framework rather than one fixed formula. A sequence transformation is described by an allowed set of edit operations, each operation receives a cost, and the distance is the minimum total cost of an edit script converting one object into another.

Classical Levenshtein distance chooses unit-cost insertion, deletion, and substitution. Hamming distance restricts the problem to positional substitutions on equal-length sequences. Insertion-deletion distance removes substitution and becomes directly related to the Longest Common Subsequence. Damerau–Levenshtein adds adjacent transposition. Weighted models change operation costs, while affine-gap models introduce state-dependent costs for runs of insertions or deletions.

Normalized Levenshtein scores form another distinct layer. Raw Levenshtein distance, post-normalized distance, normalized similarity, and path-normalized edit distance are related but not interchangeable. There is no universal normalized formula: the denominator, sequence representation, score range, zero-denominator policy, and transformation must be stated explicitly. The numerator and denominator should use the same sequence semantics, and normalization should never be confused with probability calibration.

Not every superficially similar formulation has the same mathematical properties. Classical Levenshtein and unrestricted symmetric unit-cost Damerau–Levenshtein are metrics, while Optimal String Alignment can violate triangle inequality. Arbitrary weighted costs may introduce asymmetry, and arbitrary normalized scores do not automatically inherit metricity. Specialized normalized constructions can preserve metric properties, but those properties must come from the specific definition rather than from the word “normalized.”

Some commonly discussed “variants” are actually changes at another abstraction level. Bounded edit distance changes the computational question rather than the underlying distance. Myers, Ukkonen, Landau–Vishkin, and Wagner–Fischer are algorithms for computing or exploiting edit-distance models. Approximate string matching is an application/search problem. q-Gram filters and indexes reduce candidates before exact computation.

The representation of the sequence is equally fundamental. Computing exactly the same recurrence over bytes, Unicode code points, grapheme clusters, words, phonemes, or DNA bases produces different mathematical distances. Likewise, moving from strings to trees or graphs changes both the edit operations and the computational problem.

There is therefore no universally best edit-distance variant. The correct model is the one whose primitive operations correspond to the errors, transformations, or structural changes that the application intends to measure. Only after that model has been defined should algorithm selection, indexing, normalization, thresholding, and performance engineering begin.
