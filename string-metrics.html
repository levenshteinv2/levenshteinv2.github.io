String Metrics: Distances, Similarities & Metric Properties

String metrics provide mathematical and computational ways to compare strings and other symbolic sequences. They are used in approximate matching, search, spelling correction, record linkage, entity resolution, bioinformatics, OCR, speech recognition, security, and many other systems where two sequences must be compared.

The important point is that there is no single universal definition of “string similarity.” Different comparison methods preserve different kinds of structure. Some count edit operations, some compare aligned positions, some measure shared subsequences, some compare token or q-gram overlap, and others operate on vectors, phonetic representations, or application-specific features.

Levenshtein distance is one of the foundational string metrics, but choosing a comparison method requires two separate decisions:

1. What representation or sequence is being compared?

2. What notion of difference or similarity should be measured?

The second question cannot be interpreted correctly without the first. A metric operates on the sequence supplied to it, not directly on human perception, meaning, or identity.

What Is a Mathematical Metric?

Let Σ* denote the set of all finite strings over an alphabet Σ. A mathematical metric is a function:

d : Σ* × Σ* → ℝ

that satisfies four properties.

Property Condition Meaning
Non-negativity d(x,y) ≥ 0 A distance cannot be negative.
Identity of indiscernibles d(x,y) = 0 iff x = y Only identical objects have zero distance.
Symmetry d(x,y) = d(y,x) Reversing the comparison does not change the distance.
Triangle inequality d(x,z) ≤ d(x,y) + d(y,z) An indirect route gives an upper bound on the direct distance.

A function should not be called a mathematical metric simply because a software library, database function, or API calls its output a “distance.”

Metric, Distance, Similarity, and Score Are Different Concepts

Term Typical interpretation Must satisfy metric axioms?
Metric A mathematically defined distance satisfying specific axioms Yes
Distance A larger value usually represents greater difference Not necessarily
Dissimilarity An application-defined measure of difference No
Similarity A larger value usually represents greater similarity No
Score A general comparison result used for ranking or decisions No

For example, converting a similarity using:

distance = 1 - similarity

does not automatically produce a mathematical metric. Metricity depends on the properties of the underlying comparison function.

Why Metric Properties Matter

Metric properties are not only mathematical terminology. They determine which indexing, pruning, nearest-neighbor, and search strategies are mathematically valid.

Non-Negativity

d(x,y) ≥ 0

Edit distances using nonnegative edit costs naturally satisfy this condition.

Identity of Indiscernibles

d(x,y) = 0
iff
x = y

This property becomes more subtle when preprocessing or transformation is applied.

For example:

ABC
abc

can become identical after case folding. A distance of zero then describes equality in the transformed comparison space, not necessarily equality of the original raw strings.

Symmetry

d(x,y) = d(y,x)

Standard unit-cost Levenshtein distance is symmetric. A directional weighted model does not have to be:

cost(a → b) = 0.2
cost(b → a) = 0.9

Triangle Inequality

d(x,z) ≤ d(x,y) + d(y,z)

For standard Levenshtein distance, an edit script transforming x into y can be followed by an edit script transforming y into z. The composed script may not be optimal, but it provides an upper bound for the optimal direct transformation.

Levenshtein Distance as a Metric

Standard Levenshtein distance assigns unit cost to three elementary edit operations:

insertion       = 1
deletion        = 1
substitution    = 1
match           = 0

The distance is the minimum total edit cost required to transform one sequence into another. Under this ordinary symmetric unit-cost model, Levenshtein distance satisfies the standard metric axioms.

See Edit Distance and Edit Operations & Edit Scripts for the underlying recurrence and transformation model.

Weighted Edit Distance Does Not Automatically Remain a Metric

Once edit costs depend on symbols, direction, keyboard position, phonetic similarity, context, probability, or another domain-specific model, metric properties must be checked rather than assumed.

insert(a)        = 0.7
delete(a)        = 0.7
substitute(a,e)  = 0.3
substitute(a,q)  = 1.2

A weighted distance can be extremely useful even when it is not a mathematical metric. The important requirement is to describe its semantics accurately.

See Weighted Levenshtein Distance.

The Representation Comes Before the Metric

A string metric does not compare abstract “characters” unless the application has first defined what one sequence element means.

The input sequence may consist of:

  • bytes,
  • UTF-16 code units,
  • Unicode code points,
  • Unicode scalar values,
  • extended grapheme clusters,
  • application-defined characters,
  • words,
  • tokens,
  • phonemes,
  • q-grams,
  • events,
  • or other symbolic units.
representation
+
comparison function
=
operational notion of difference

The same mathematical algorithm can therefore return different numerical results when it operates on different sequence representations.

Character-Level vs Token-Level Distance

Consider:

the black cat
the cat

At word-token level:

[the, black, cat]
[the, cat]

the transformation can be represented as one token deletion. At code-point or character level, several sequence elements must be deleted.

Neither result is inherently wrong. They answer different questions because the unit of comparison is different.

Unicode Representation and String Metrics

Unicode makes sequence representation especially important. A visible accented character can have more than one code-point representation.

For example, a visible é can be represented as:

U+00E9

or:

U+0065
+
U+0301

A raw code-point comparison can distinguish these two sequences even though they are canonically equivalent.

Likewise, a single user-perceived emoji or decorated symbol can contain several code points while forming one extended grapheme cluster.

For multilingual or user-facing text, normalization, segmentation, representation, and metric selection should therefore be defined together.

See Unicode & Grapheme-Safe Levenshtein.

Transformation Defines the Comparison Space

Many applications transform text before calculating a metric. Let T(x) represent an application-defined transformation. The system then evaluates:

dT(x,y) = d(T(x), T(y))

The resulting value describes the distance between the transformed representations, not necessarily between the original raw inputs.

Transformations may include:

  • Unicode normalization,
  • case folding,
  • accent or diacritic policies,
  • transliteration,
  • phonetic encoding,
  • tokenization,
  • q-gram extraction,
  • or application-specific canonicalization.

For the broader relation between text transformation and sequence comparison, see Unicode Text Transformations.

Major Families of String Comparison

Family Typical representation Main idea
Edit distances Ordered sequence Minimum transformation cost
Positional distances Aligned positions Count positional disagreement
Subsequence methods Ordered subsequences Measure preserved order
Set-based methods Sets, multisets, q-grams Measure overlap
Vector methods Frequency or feature vectors Compare vector geometry
Name comparators Characters plus heuristics Model common name variations
Phonetic methods Phonetic representations Compare approximate pronunciation
Semantic methods Meaning-oriented representations Compare semantics rather than spelling

Hamming Distance

Hamming distance counts the positions at which two aligned sequences differ. In its classical form it applies to equal-length sequences.

x = abcdef
y = abcxef

Hamming distance = 1

Hamming distance is a genuine metric on fixed-length sequences. It models positional substitutions but does not perform insertion/deletion alignment.

Levenshtein vs Hamming Distance

Levenshtein distance also permits insertions and deletions.

x = abc
y = abxc

Levenshtein distance = 1

Classical Hamming distance is not directly defined for this pair because the sequence lengths differ.

For equal-length strings, Hamming distance provides an upper bound on ordinary Levenshtein distance, because substitution can always repair an aligned mismatch while Levenshtein may sometimes find an even cheaper insertion/deletion alignment.

Damerau-Levenshtein and Transpositions

Standard Levenshtein distance does not treat an adjacent transposition as a primitive one-cost edit.

abcd
abdc

Classical Levenshtein can repair this difference using two elementary edits. A Damerau-style model can treat the adjacent swap:

cd → dc

as a transposition operation. Different Damerau variants must still be distinguished because they do not necessarily define the same operation semantics or mathematical properties.

See Damerau-Levenshtein Distance.

Longest Common Subsequence and Indel Distance

A longest common subsequence (LCS) preserves relative order while allowing elements to be skipped. Let:

L(x,y) = length of a longest common subsequence

An insertion-deletion distance can then be defined as:

dIndel(x,y) = |x| + |y| - 2L(x,y)

This distance is often called Indel distance. Its primitive edit operations are insertion and deletion. A substitution is not a primitive cost-1 operation. Replacing one symbol with another requires deleting one symbol and inserting the other, so the corresponding cost is typically 2.

Levenshtein, Indel Distance, LCS and Ratio Scores

Levenshtein distance and Indel distance are closely related, but they are not interchangeable. This distinction becomes particularly important when software exposes a generic function named ratio, similarity, or normalized_similarity.

Measure Primitive operations Typical substitution cost Main interpretation
Levenshtein distance Insertion, deletion, substitution 1 Minimum number or cost of ordinary edits
Indel distance Insertion, deletion Equivalent to delete + insert Insertion/deletion transformation cost
LCS length Not itself an edit operation model Not applicable Amount of ordered subsequence preserved
Ratio / similarity score Depends on implementation Depends on underlying measure Usually a normalized ranking score

A useful identity links LCS and Indel distance:

dIndel(x,y) = |x| + |y| - 2LCS(x,y)

This does not mean that ordinary Levenshtein distance always has the same value. Classical Levenshtein allows a substitution to cost 1, while an insertion/deletion-only model normally represents the same replacement using two edits.

For example:

x = cat
y = cut

Levenshtein distance:
a → u
distance = 1

Indel distance:
delete a
insert u
distance = 2

Therefore the name of a software function is not sufficient to identify its mathematical semantics. A function called ratio may be based on normalized Levenshtein distance, normalized Indel distance, LCS-derived similarity, or another scoring rule.

This distinction appears in real string-matching libraries: some APIs associated with “Levenshtein” terminology expose ratio functions whose underlying score is based on Indel similarity rather than classical unit-cost Levenshtein distance.

When reproducibility matters, record the exact comparison function rather than only the API name:

sequence representation
+
allowed operations
+
operation costs
+
normalization formula
+
score range
=
actual comparison semantics

For a broader taxonomy of edit-distance models, including normalized and weighted variants, see Edit Distance Variants.

Set-Based String Similarity

A string can be transformed into a set or multiset before comparison. For example:

abcd

bigrams:
ab
bc
cd

The comparison then operates on the derived representation rather than directly on the original ordered character sequence. This transformation can intentionally discard some information while preserving other information.

Jaccard Similarity and Distance

For sets A and B:

J(A,B) = |A ∩ B| / |A ∪ B|

Jaccard distance is:

dJ(A,B) = 1 - J(A,B)

Jaccard distance is a metric on sets, but the representation still determines what the result means.

Consider:

x = abc
y = cba

As character sets:

{a,b,c}
{a,b,c}

their Jaccard distance is zero because converting the strings into sets removed all sequence-order information.

q-Gram Representations

q-Grams preserve some local ordering by extracting overlapping substrings of fixed length.

abcd
↓
ab, bc, cd

q-Grams can be represented as sets, multisets, frequency vectors, or weighted feature vectors. They are useful both as direct similarity representations and as candidate-generation features before exact edit-distance verification.

See Indexing and Filtering for Edit Distance.

Cosine Similarity

Strings can also be transformed into token-frequency, character-frequency, or q-gram-frequency vectors. For nonzero vectors:

cos(x,y) = (x · y) / (||x|| ||y||)

Values closer to one indicate more similar vector direction.

The common transformation:

1 - cosine_similarity

should not automatically be assumed to satisfy all mathematical metric axioms.

Jaro and Jaro-Winkler Similarity

Jaro similarity compares short strings using matching characters within a positional window and a transposition-related disagreement term.

Jaro-Winkler adds an adjustment for a bounded common prefix:

JW = J + lp(1 - J)

where J is Jaro similarity, l is a bounded common-prefix length, and p is the prefix scaling factor.

This weighting can be useful for some name-matching tasks, but it is an application-oriented model rather than a universal definition of string similarity.

Different String Metrics Can Produce Different Answers

Consider:

x = abcd
y = abdc
Method Possible result What it emphasizes
Levenshtein 2 Insertion, deletion, substitution
Damerau-style 1 Adjacent transposition
Hamming 2 Aligned positional mismatches
Indel / LCS distance 2 Preserved ordered subsequence
Character-set Jaccard 0 Set membership while ignoring order

These results are not contradictions. Each method defines a different comparison space and preserves different information.

Numerical Normalization Is Not Unicode Normalization

The word normalization is used for two completely different concepts in string processing.

A numerical distance can be normalized, for example:

dN(x,y) =
dlev(x,y)
/
max(|x|, |y|)

and converted to a similarity:

s(x,y) = 1 - dN(x,y)

This operation changes a numerical result.

Unicode NFC, NFD, NFKC, and NFKD instead transform the input sequence itself.

numerical normalization
≠
Unicode normalization

The two operations belong to different layers of the comparison pipeline.

There Is No Single Universal Normalized Levenshtein Score

A raw Levenshtein distance is an integer edit cost under the chosen operation model. Turning that value into a relative score requires an additional convention.

Common choices can involve:

  • the maximum sequence length,
  • the minimum sequence length,
  • the sum of sequence lengths,
  • an alignment or path length,
  • or another task-specific denominator.

Different denominators produce different numerical semantics. A system should therefore document both the raw distance definition and the normalization formula.

For the broader treatment of normalized edit distance, see Edit Distance Variants.

Normalizing a Metric Can Break Metric Properties

Dividing a valid metric by a denominator that depends on the particular pair being compared does not guarantee that all original metric properties are preserved.

A convenient score in the range 0..1 should therefore not automatically be described as a mathematical metric.

Metric Properties Enable Exact Search Pruning

Triangle inequality has direct computational value. Let:

q = query
p = pivot
x = candidate

For a metric:

|d(q,p) - d(x,p)| ≤ d(q,x)

If the search radius is r and:

|d(q,p) - d(x,p)| > r

then:

d(q,x) > r

and the candidate can be rejected without directly computing its distance from the query.

This is one reason the distinction between a true metric and an arbitrary similarity score matters in large-scale retrieval.

See Indexing and Filtering for Edit Distance.

String Similarity Is Not Semantic Similarity

String metrics compare representations rather than meaning.

car
automobile

can be semantically close while having substantial character-level distance.

Meanwhile:

cat
car

are lexically close but describe different concepts.

string similarity
≠
semantic similarity

See String Similarity vs Semantic Similarity.

String Similarity Does Not Establish Entity Identity

Two strings can be close without representing the same real-world person, organization, place, product, citation, account, or database record.

small distance
≠
same entity

The reverse is also true. Aliases, abbreviations, transliteration, historical spelling, name changes, and multilingual representations can produce very different strings for the same entity.

String similarity should therefore be treated as evidence about representations, not as automatic proof of identity.

For identity-oriented matching systems, see Entity Resolution and Record Linkage.

Choosing a String Metric

Problem structure Reasonable starting point
Equal-length aligned symbols Hamming distance
Insertions, deletions and substitutions Levenshtein distance
Only insertion/deletion structure matters Indel / LCS-based distance
Adjacent swaps are important Damerau-style distance
Error probabilities or operation costs are known Weighted edit distance
Ordered subsequences matter LCS-based comparison
Token or q-gram overlap matters Jaccard-style comparison
Feature-frequency geometry matters Cosine or vector comparison
Short human names Evaluate multiple lexical and phonetic comparators
Meaning matters more than spelling Semantic representations
Metric-space indexing is required Use a comparison function with proven metric properties

How to Evaluate a String Metric

Metric selection should be evaluated against the actual application rather than a small set of intuitive examples. A useful evaluation specifies:

target task
+
sequence representation
+
preprocessing policy
+
comparison function
+
representative labeled data
+
threshold or ranking rule
+
quality metric
+
computational cost

Depending on the application, evaluation may measure:

  • precision,
  • recall,
  • ranking quality,
  • nearest-neighbor accuracy,
  • candidate recall,
  • candidate-set size,
  • false merge and false split rates,
  • latency,
  • memory use,
  • and throughput.

Comparison Function and Candidate Generation Are Separate Decisions

Choosing Levenshtein distance as the final verifier does not imply that every item in a large collection should be compared against every other item.

A scalable system can instead use:

index / blocking / filter
↓
candidate set
↓
string metric
↓
verification / ranking / decision

Candidate generation and final comparison are separate modeling decisions. A highly accurate string metric cannot recover a correct match that never entered the candidate set.

See Indexing and Filtering for Edit Distance.

raw text
↓
transformation / normalization policy
↓
segmentation
↓
sequence representation
↓
comparison function
↓
distance or similarity
↓
normalization / threshold / ranking
↓
application decision

For Unicode text this may become:

Unicode input
↓
normalization policy
↓
grapheme or code-point segmentation
↓
sequence representation
↓
Levenshtein or another string metric
↓
normalized score / threshold
↓
application decision

The metric is one layer of the system. It does not determine all preprocessing, representation, retrieval, ranking, or identity decisions around it.

Why Levenshtein Distance Remains Foundational

Levenshtein distance remains foundational because its operation model is simple and general:

insertion
deletion
substitution

These operations connect naturally to dynamic programming, approximate string matching, metric-space search, weighted extensions, sequence alignment, Unicode-aware implementations, and many application-specific comparison pipelines.

Its limitations are equally important. Standard Levenshtein distance does not inherently model:

  • adjacent transpositions as one elementary edit,
  • phonetic equivalence,
  • semantic similarity,
  • visual glyph similarity,
  • token reordering,
  • Unicode grapheme boundaries,
  • or domain-specific error probabilities.

Those boundaries are useful because they make representation and modeling choices explicit.

String Metrics and Unicode Text Transformations

Unicode transformations provide a useful example of the distinction between changing a representation and measuring the distance between representations.

source text
↓
transformation T
↓
transformed sequence
↓
metric d
↓
distance or similarity

Canonical normalization can collapse canonically equivalent sequences. Compatibility normalization can collapse a broader class of representational distinctions. Transliteration can move text between writing systems. Other Unicode transformations can create a different sequence for presentation or application purposes.

The underlying comparison function can remain Levenshtein distance even though the sequence supplied to it has changed.

Continue with Unicode Text Transformations.

Summary

String metrics quantify relationships between representations. Standard unit-cost Levenshtein distance is a mathematical metric under its ordinary insertion, deletion, and substitution model, but many useful comparison scores do not necessarily satisfy metric axioms.

Representation is as important as the comparison function itself. Bytes, UTF-16 code units, Unicode code points, grapheme clusters, words, tokens, q-grams, phonemes, and other units define different sequence spaces.

Levenshtein distance must also be distinguished from related models. In particular, Indel distance permits insertion and deletion but does not treat substitution as a primitive unit-cost edit. It is directly related to the longest common subsequence. A software function called ratio or similarity therefore should not be assumed to represent normalized classical Levenshtein distance without checking its actual definition.

Numerical normalization, Unicode normalization, sequence representation, candidate generation, metric choice, and application decisions are separate layers.

Choose the representation first. Choose the comparison function second. Document the exact scoring rule. Interpret the result only within the comparison space defined by those choices.
