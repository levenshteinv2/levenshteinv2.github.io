Unicode Homoglyph and Confusable Attacks: Edit Distance, UTS #39, IDN Spoofing, and Defense

Unicode Homoglyph and Confusable Attacks: Edit Distance, UTS #39, IDN Spoofing, and Defense

Unicode allows software to represent writing systems from around the world, but different Unicode strings can sometimes appear sufficiently similar that a human reader mistakes one identifier for another.

This becomes a security problem when text controls identity or authority, including domain names, usernames, package names, repository names, source-code identifiers, email addresses, certificate names, file names, and other security-sensitive labels.

machine identity:
different

human perception:
possibly similar

Unicode confusable analysis and Levenshtein distance address related but different parts of this problem. Unicode security mechanisms model known confusable relationships and identifier policies. Levenshtein distance measures sequence edits between defined representations.

Character Identity and Visual Appearance Are Different

Unicode characters are identified by code points and properties, not by a guarantee that every character has a unique visual shape.

Characters from different scripts can look similar depending on the font, size, rendering environment, and reader.

A familiar example is the Latin small letter a and Cyrillic small letter а. They can look very similar while remaining different Unicode characters.

Latin:
a

Cyrillic:
а

code-point identity:
different

The same principle applies to many other characters and sequences.

visual resemblance
≠
Unicode identity

Homoglyph, Homograph, and Confusable

These terms are related but should not be treated as perfect synonyms.

Term Useful interpretation
Glyph A rendered visual form
Homoglyph Characters or glyph forms that appear alike
Homograph Written identifiers or words that can appear alike
Confusable A security-oriented Unicode relationship used to detect possible visual confusion

Unicode security work should rely on the terminology and mechanisms defined by the relevant Unicode specifications rather than on appearance alone.

What UTS #39 Provides

Unicode Technical Standard #39, Unicode Security Mechanisms, defines mechanisms for detecting and managing security risks associated with Unicode identifiers.

Its scope includes:

  • identifier security profiles,
  • confusable detection,
  • single-script confusables,
  • mixed-script confusables,
  • whole-script confusables,
  • script analysis,
  • restriction levels,
  • mixed-number detection,
  • and related identifier-security mechanisms.

A system can support Unicode correctly while still applying an unsafe identifier policy. Unicode encoding support and Unicode security are therefore separate concerns.

Confusable Skeletons

UTS #39 defines security-oriented transformations that allow strings to be compared through confusable representations derived from the official Unicode confusables data.

At a high level:

identifier
↓
UTS #39 security processing
↓
confusable skeleton
↓
comparison

If two strings produce equal skeleton representations under the applicable UTS #39 procedure, they can satisfy the specification's confusable relation.

skeleton(A)
=
skeleton(B)

→
confusable under the defined procedure

The actual algorithm is versioned and depends on official Unicode security data. Production implementations should use the current specification and data rather than reconstructing the mechanism from simplified examples.

A Skeleton Is Not User Text

A confusable skeleton is a comparison representation for security analysis. It should not be treated as a linguistically correct replacement for the original identifier.

original identifier
=
source / display representation

confusable skeleton
=
security comparison representation

Replacing user-visible text with the skeleton could destroy legitimate distinctions.

Skeleton equality also does not establish identity or intent.

same skeleton
≠
same real-world entity

same skeleton
≠
malicious intent

It is a security signal that must be interpreted together with application context and provenance.

Single-Script, Mixed-Script, and Whole-Script Confusables

UTS #39 distinguishes several confusable cases.

Single-Script Confusables

Two strings can be confusable while remaining compatible with the same writing system.

This matters because simply prohibiting mixed scripts cannot eliminate all confusable identifiers.

Mixed-Script Confusables

A deceptive identifier can combine characters associated with different scripts.

Latin-looking identifier
+
one or more visually similar characters from another script

Whole-Script Confusables

Two strings can each be single-script while belonging to different scripts and still be confusable.

This establishes an important rule:

mixed-script detection
is useful

but

mixed-script detection
is not sufficient

Multiple Scripts Do Not Automatically Mean an Attack

Legitimate multilingual text can use more than one script.

Japanese text, for example, can naturally involve Han, Hiragana, Katakana, Latin characters, punctuation, and other shared characters.

Unicode also defines Script and Script_Extensions properties because the relationship between characters and writing systems is more complex than assigning every character to one exclusive script.

mixed script
≠
malicious

Security policy must distinguish legitimate multilingual usage from unexpected ambiguity.

Restriction Levels Are Classification Signals

UTS #39 defines restriction levels for identifiers, including:

  • ASCII-Only,
  • Single Script,
  • Highly Restrictive,
  • Moderately Restrictive,
  • Minimally Restrictive,
  • and Unrestricted.

These levels characterize script and identifier-profile usage. They are not probabilities that a string is malicious.

Single Script
≠
safe

Unrestricted
≠
proof of attack

Mixed-Number Systems

Unicode contains decimal digits from multiple numbering systems. Some of these digits can be visually confused with digits from another system.

UTS #39 therefore treats mixed-number detection as a distinct mechanism.

mixed-number detection
≠
ordinary mixed-script detection

Unicode Normalization Solves a Different Problem

Unicode normalization deals primarily with defined representation equivalence.

For example, an accented character can have precomposed and decomposed representations:

é

and

e + ◌́

NFC and NFD address canonical equivalence. NFKC and NFKD additionally process compatibility relationships.

They do not provide universal visual canonicalization.

Unicode normalization
≠
confusable detection

Cross-script lookalikes can remain different after normalization.

See Text Normalization and Transliteration .

Grapheme Clusters Do Not Solve Visual Confusability

Extended grapheme clusters provide useful boundaries for user-perceived text units, but they remain text-segmentation units rather than glyph-similarity models.

code point
≠
grapheme cluster
≠
glyph

A grapheme-aware Levenshtein implementation can improve the interpretation of text edits when visible character units matter. It does not make Levenshtein distance a visual-confusability algorithm.

See Unicode & Grapheme-Safe Levenshtein .

Where Levenshtein Distance Fits

Many deceptive identifiers differ from a protected identifier through a small number of substitutions, insertions, or deletions.

protected identifier
↓
small spelling mutation
↓
candidate identifier

Standard Levenshtein distance can identify strings that are lexically close.

It does not understand visual appearance.

Levenshtein:
sequence edits

UTS #39:
Unicode security relationships

These mechanisms are complementary rather than interchangeable.

Weighted Edit Distance

An application can assign different edit costs to different substitutions. A substitution known to be relevant in a particular domain can receive a lower cost than an unrelated substitution.

cost(expected variation)
=
lower

cost(unrelated substitution)
=
higher

This idea is related to Weighted Levenshtein Distance .

For Unicode security, however, application-defined weighting should not replace the standardized Unicode confusables data and security mechanisms.

Multi-View Security Comparison

A robust detector can preserve several representations of the same identifier rather than reducing every problem to one string.

raw identifier
      │
      ├── normalized representation
      ├── code-point representation
      ├── grapheme representation
      ├── script analysis
      └── confusable skeleton

Features can then include:

  • raw edit distance,
  • normalized edit distance,
  • grapheme-level distance where appropriate,
  • confusable-skeleton equality,
  • script relationships,
  • restriction level,
  • mixed-number signals,
  • identifier-profile violations,
  • and application-specific provenance.

Levenshtein Distance Between Security Representations

An application can additionally calculate edit distance between security-derived representations:

ED(
  skeleton(A),
  skeleton(B)
)

This can be useful for searching around a protected identifier when a candidate contains both confusable substitutions and ordinary spelling changes.

This is an application-defined extension. It is not the formal definition of UTS #39 confusability.

skeleton(A) = skeleton(B)
→
defined confusable relationship

ED(skeleton(A), skeleton(B)) ≤ k
→
application-defined near-confusable search

The two concepts should remain separate.

Unicode Transformations Can Have Opposite Goals

Unicode strings can be transformed for very different purposes.

Transformation Primary purpose
NFC / NFD Canonical representation
NFKC / NFKD Compatibility-oriented representation
Transliteration Representation across writing systems
Presentation-oriented mapping Alternative visual presentation
Confusable skeleton Security comparison

A presentation-oriented transformation may deliberately preserve an alternative representation. Security processing may instead map known confusable representations toward a common comparison representation.

The general transformation model is described in Unicode Text Transformations .

Internationalized Domain Names

Internationalized Domain Names are an important environment for Unicode identifier security.

IDNA provides standardized processing for internationalized domain labels. An ASCII-compatible encoded label can use the xn-- prefix.

The presence of Punycode does not itself indicate phishing, and successful IDNA processing does not prove that a domain is safe.

Punycode
≠
phishing

valid IDN
≠
trusted identity

Domain-name security also depends on registry policy, script restrictions, browser behavior, protected-name comparison, and other identity signals.

HTTPS Does Not Solve Visual Impersonation

TLS can authenticate a connection to the domain that was actually requested.

It does not establish that a visually similar domain belongs to the organization a user intended to visit.

TLS:
connection to requested origin

visual recognition:
human interpretation of identifier

These are different security layers.

Typosquatting and Unicode Confusables

Typosquatting and homoglyph attacks overlap but are not the same technique.

Ordinary typosquatting can use:

  • insertions,
  • deletions,
  • substitutions,
  • transpositions,
  • or other spelling variations.

Unicode confusable attacks can exploit visual relationships between different Unicode characters or sequences.

A real detector can therefore combine lexical-distance and Unicode-security signals rather than forcing both problems into one metric.

Continue with Typosquatting and Software Supply-Chain Security .

Package and Repository Names

Similar risks occur outside domain names.

Package registries, repositories, dependencies, usernames, and other software identifiers can all be targeted by names that resemble trusted identifiers.

Edit distance can help identify nearby names, while Unicode security mechanisms can identify confusable relationships that plain edit distance does not understand.

Neither signal proves malicious intent.

Do Not Use Similarity as Authentication Equality

Fuzzy matching answers questions such as:

Could these identifiers be related or easily confused?

Authentication asks:

Does this credential belong to this exact account identity?

These questions must not be merged.

small edit distance
≠
same account

confusable skeleton equality
≠
same account

Security-sensitive identity decisions require exact identity rules and appropriate authentication evidence.

False Positives Matter

A Unicode security detector that blocks all unfamiliar scripts or every mixed-script string will produce false positives for legitimate international users.

Likewise, a detector that flags every identifier within a small edit distance of a popular name will catch many unrelated strings.

A useful system combines several signals and applies policies appropriate to its namespace and threat model.

similarity signal
+
Unicode security signal
+
namespace policy
+
provenance
+
context
↓
security decision

Version Unicode Security Data Explicitly

Unicode security data and algorithms evolve as Unicode adds characters, scripts, properties, and updated mappings.

A reproducible implementation should record at least:

  • Unicode version,
  • UTS #39 revision,
  • confusables-data version,
  • normalization implementation,
  • and application security-policy version.

Stored security comparison representations may need to be recomputed when the Unicode security data used by the system changes.

A Layered Detection Model

No single string metric is sufficient for Unicode identifier security.

Control Useful for Main limitation
Unicode normalization Representation equivalence Does not solve arbitrary confusables
Script policy Unexpected script combinations Does not eliminate whole-script confusables
UTS #39 confusable processing Known Unicode confusable relationships Does not establish malicious intent
Levenshtein distance Typos and nearby sequence variants No intrinsic visual semantics
Rendering analysis Environment-specific visual resemblance Depends on font and rendering environment
Provenance and identity data Real-world identity evidence Does not itself detect visual confusion

Relationship to Unicode Text Transformations

Unicode security demonstrates an important property of text processing: the same source string can be transformed into different representations for different purposes.

source Unicode text
        │
        ├── normalization
        ├── transliteration
        ├── presentation-oriented transformation
        └── security transformation

A confusable skeleton is a security-oriented comparison representation. Other Unicode transformations can have entirely different goals.

Levenshtein distance can compare resulting sequences, but the transformation policy determines what those sequences represent.

See Unicode Text Transformations .

Summary

Unicode homoglyph and confusable attacks exploit the difference between encoded character identity and human visual perception.

Unicode normalization handles defined representation equivalence but does not provide universal visual canonicalization. UTS #39 provides dedicated security mechanisms for identifier profiles, confusable detection, script analysis, restriction levels, mixed-number systems, and security-oriented comparison representations.

Levenshtein distance complements those mechanisms by measuring sequence edits and finding nearby lexical variants. It does not provide a model of glyph appearance and does not establish malicious intent.

Unicode security defines the security representation. Levenshtein measures sequence difference. Identity and intent require additional evidence.
